# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A **Safari web extension** (Manifest v3, macOS and iOS) that hides every picture on a web page until it has been checked, and greys out human skin (MediaPipe's selfie segmentation model, in WebAssembly, inside the extension). On the Mac a small **host app** runs as a background watcher that keeps the extension switched on and installs updates. The use case is religious compliance — all images must be filtered before being shown.

**There is no server** (since 1.10.0, 2026-11-23; see *Serverless* below). Until then the Mac sent every picture to a local Python/Flask server (`server/`, removed; it is in the git history).

## Architecture

```
Web Page → content.js (≤768px JPEG) → background.js → ondevice/engine.js (MediaPipe WASM, GPU→CPU fallback)
Web Page ← content.js paints grey over the full-res image ← skin mask (run-length encoded) ← background.js
```

Images are hidden immediately when a page loads (`opacity: 0`), checked by the engine in the extension's background page, then revealed. **Images remain hidden if they can't be checked** (the engine fails to load, a picture can't be read) — this is intentional for religious compliance, not a bug.

### Extension (Safari / Xcode)

- **Content scripts** (all in `Shared/Extension/`, loaded in this order, sharing `globalThis.__ifs` in the isolated world):
  - `content-core.js` — hide-until-checked CSS for the document **and every shadow root**, shadow-root registry + observer, `IFS.checkUrl` (picture by URL, cached per page) / `IFS.checkCanvas` (pixels we drew: video frames, inline-SVG rasters), engine selection, enable/disable fan-out.
  - `content.js` — `<img>`/`<picture>` (canvas → base64 → background; `MutationObserver` + 250 ms scan for lazy images). Exposes `__ifs.img` so the core can hand it images inside shadow roots.
  - `content-elements.js` — inline `<svg>` (rasterised with computed styles, checked; shown live if clean, else the filtered raster replaces it), `<svg><image>`, `<input type=image>`, `<object>`/`<embed>` images.
  - `content-backgrounds.js` — CSS `background-image` / `list-style-image` / `border-image`, on elements and `::before`/`::after` (incl. `content: url()`).
  - `content-video.js` — `<video>`: never shown; an overlay canvas draws only checked frames.
- **`page-world.js`** — runs in the page's own JS world (registered by `background.js` via `scripting.registerContentScripts({ world: 'MAIN' })`; Safari ignores `"world"` in the manifest). Forces every shadow root open + adopts a stopgap hide sheet at creation; blocks page scripts from native video fullscreen / Picture in Picture. Puts every replaced browser function back as soon as a Cloudflare challenge script appears or the site turns out to be excluded, and isn't injected into captcha frames (see *Bot checks* below).

### Bot checks (Cloudflare and captchas)

Found 2026-11-23 (owner: the extension "is breaking and triggering websites and cloudflare bot checks"). Three ways the extension looked like a bot:
- **`page-world.js` replaced built-in DOM functions** (`Element.prototype.attachShadow`, `requestFullscreen`, `HTMLVideoElement` fullscreen/PiP) in every frame, including Cloudflare's own challenge frame, and forced Turnstile's **closed shadow root** open: exactly what captcha-solving tools do. Cloudflare's managed challenge treats a page whose DOM functions aren't the browser's own as a bot. A single pass-through wrapper around `document.createElement` from another extension was enough to lock people out (KDE bug 487303). Now:
  - not injected into captcha frames (`PAGE_WORLD_EXCLUDE` in `background.js`: `challenges.cloudflare.com`, `*.hcaptcha.com`, reCAPTCHA, Arkose/FunCaptcha, DataDome). Those frames have no shadow-DOM pictures or videos; their pictures (a captcha photo grid) are still filtered by the content scripts. The content scripts skip only `challenges.cloudflare.com` (manifest `exclude_matches`), which has no pictures at all. An existing registration is replaced once (`PAGE_WORLD_VERSION`, stored as `pageWorldVersion`); if registering with exclusions fails, the old definition is registered so pages are never left without it.
  - on a page that adds a Cloudflare challenge script (`…/cdn-cgi/challenge-platform/h/…`, the "Just a moment..." page; `challenges.cloudflare.com/turnstile/…`, a Turnstile widget), a main-world `MutationObserver` puts every replaced property back **before that script runs**, with its original descriptor (same function objects and flags), and removes the `__ifsPageWorld` global. Measured in a harness (Chromium): the challenge script saw native functions, identical descriptors and a closed root that stayed closed, for a script the parser added and one a script added; the old code showed it the replacements.
  - on an excluded site (or with filtering off on iOS) `content.js` dispatches `ifs-release-page-world` and `page-world.js` does the same release, so an excluded site is exactly as Safari made it.
  - Cost: on those pages, shadow roots created later aren't forced open (a closed one with pictures in it isn't filtered) and page scripts get native video fullscreen. Cloudflare's background bot detection (`…/challenge-platform/scripts/jsd/`, on ordinary pages of many sites, in a hidden blank frame) deliberately does **not** trigger the release: that would drop the protection on a large part of the web, with no evidence it matters. Extend `CHALLENGE_SRC` if it does.
- **The server downloaded pictures itself** with `python-requests` and a Safari user agent, from this Mac's IP, whenever the background's own download failed, including 403/404 answers (server log: 403 from makerworld.com and ivelt.com, both Cloudflare). Bot traffic from an address makes Cloudflare challenge the real browser on it more often. Gone with the server (1.10.0): a picture the page won't let the content script read is downloaded by the background page itself, through Safari (its cookies, its network stack), and an error fails closed.
- Not verified: anything in real Safari against a live Cloudflare challenge (only the harness above); whether WebKit's parser always gives the observer a chance before a *synchronous*, already-cached `<script src>` runs (async/dynamic scripts, which Cloudflare's are, always do); whether Turnstile on a host page inspects that page's functions at all.
- **`Shared/Extension/background.js`** — Receives check requests from the content scripts and runs them through the engine (`ondevice/engine.js`, loaded with `import()`), caches results per URL, keeps the config in `browser.storage.local` (enabled state on iOS, excluded sites, the Mac's exclusion password), registers `page-world.js`.
- **`Shared/Extension/ondevice/`** — the engine: `engine.js` (ours) plus MediaPipe tasks-vision 0.10.32 and the `selfie_multiclass_256x256.tflite` model (~27 MB; an explicit folder in both extension targets, see *The filter engine*).
- **`macOS/Extension/SafariWebExtensionHandler.swift`**, **`iOS/Extension/…`** — the native handlers Safari requires; both just answer (nothing to start).
- **`macOS/App/AppDelegate.swift`** — opened normally: the setup window. With `--start-server-only` (the LaunchAgent; the name is from the server days and kept so installed agents keep working): the always-on background watcher, which starts the enforcer and the updater, and once removes what the old Python server left behind (`LegacyServerCleanup`: stops a server still running from its own PID file, deletes the virtualenv and the bytecode cache; never the logs, `Updates.noindex` or `review/`). Safari **and Safari "Add to Dock" web apps** count as Safari: web apps are separate processes with bundle ID `com.apple.Safari.WebApp.<UUID>` that load the extension.
- **`macOS/App/ExtensionEnforcer.swift`, `ExtensionGate.swift`, `SafariProfileSettings.swift`** — keep the extension switched on in every Safari profile in use (see *Extension enforcement* below). Only in the watcher; the normal app window is unchanged.

### Tabs Safari never connects to the extension (macOS)

Found 2026-11-23 (owner: "half the time the image doesn't render or load"). Safari 27.2 sometimes gives a tab a web view it never connects to the extension. WebKit logs `web view 0x… returned by webViewForWebExtensionContext: is not configured with a WKWebExtensionController` (`log show --predicate 'subsystem == "com.apple.WebKit" AND category == "Extensions"'`), repeated for as long as the tab lives. Our content scripts still run there, but **without `browser`** (console: `ReferenceError: Can't find variable: browser` at `content-core.js`/`content.js`; AdBlock's `ewe-content.js` loses its API in the same frames). Nothing can be checked, so every picture in that tab stays hidden, for **every page loaded in it**: a reload in that tab was measured still broken. A new tab works. Seen: one such web view at every Safari launch (the first tab of the session), and one created half a second after an iCloud Tabs / Tab Groups sync (`com.apple.Safari:TabGroup` "Sync reload completed"). Same symptom as WebKit bug 294769 (fixed 2025 for a different cause: extension loaded after the page).
- **No automatic fix.** Open the page in a new tab. (A reload of the same tab stays broken.)
- **Do not reopen or reload tabs automatically: tried in 1.11.1-1.11.3, removed in 1.11.4.** The background page pinged tabs and reopened (`tabs.create` + `tabs.remove`) one whose content scripts refused the message twice. "No content script answers" is not specific to this bug: a page that **failed to load** (Safari's "can't open the page" screen keeps the https URL) has no content scripts either. On 2026-11-24 it reopened 8 times, twice each for `filter.felzy`, `www.google.com/search`, `github.com/logout` and `help.github.com/contact`; the new tabs didn't answer either. Safari's log has 83 `didFailProvisionalLoad` lines in those minutes (matched by time; a mock of a refused message reproduces it in 1.11.3: two reopens, then the limit). That drops the tab's history, requests an address again that may have side effects or work only once, and it never had a confirmed repair of a really unconnected tab. It had been tested on a healthy tab, never on a failed load. A future attempt needs a signal only the bug produces, and should tell the user rather than act.
- Without the API the content scripts don't throw half-way: everything stays hidden, every check fails, no other module breaks (`IFS.api` is null; harness-checked: no exception, `<img>`, CSS picture and SVG stay hidden).
- Development only: an xcodebuild/Xcode build registers its own copy, and a running Safari can switch to it within seconds (seen 2026-11-23); tabs already open then have dead content scripts. Build with Safari closed and unregister the build's copies before reopening it.
- **Debugging a "pictures don't load" report:** on this Mac, Safari's Develop → *Allow JavaScript from Apple Events* is on, so `osascript -e 'tell application "Safari" to do JavaScript "…" in tab N of window M'` reads `data-filter-processed` on every `<img>` of a real tab (page world; the attributes are on the DOM). All `none` with `style[data-ifs-style]` present = the content scripts died (this bug); `processing` stuck = a check without a reply; `failed` = the engine refused.

### Keeping the extension light (content-script cost)

The content scripts run in **every tab and every iframe**, so what they cost when nothing is happening matters as much as what they cost under load. Found on 2026-11-10 from macOS CPU-resource reports (`/Library/Logs/DiagnosticReports/com.apple.WebKit.WebContent_*.cpu_resource.diag`, 56% → 64% → 74% of a core for two minutes): a WebContent process spent its time inside a `MutationObserver` callback calling `getComputedStyle(...).getPropertyValue(...)`, i.e. `content-backgrounds.js` re-probing hundreds of elements (each probe flips an attribute and forces a style recalculation) on every class/inline-style mutation of a page that never stops mutating.

Rules that keep it cheap (all of them keep the safety rule: every CSS picture is suppressed by stylesheet until probed and checked, so *when* something is re-read is latency, never a leak):
- **No unconditional timers.** Poll through `IFS.shouldPoll(key, idleEveryMs, activeEveryMs)` (`content-core.js`): full speed only for 3 s after activity (`IFS.touch()`: a mutation, a load, scroll, resize, tab shown), slower when still, **never in a hidden tab**. The whole-document shadow-root walk runs only when nodes were added (or every 2 s). The 10 s background sweep runs only if something happened (or once a minute), skips elements probed in the last 30 s, and decides "near the viewport" per chunk, not for every element up front.
- **Bound the work per mutation** (`content-backgrounds.js`): an inline-style change is re-probed only if the old or new style text mentions `background`, `list-style`, `border-image`, `content`, `url(`, a custom property or `all` (`attributeOldValue` is on in the core observer for this; `transform`/`opacity`/`left` animations cost nothing); a class/id change re-probes the element and at most 40 descendants, a bigger subtree is re-read separately (once a second per element, chunked); attribute-driven probes are throttled to a leading edge plus one trailing batch per 120 ms; a batch probes 200 elements at once and the rest in chunks across frames.
- **What must stay synchronous** is only what protects the rule without a style recalculation: `coverInlineImportant` covers a page's inline `!important` picture (which beats the suppression stylesheet) before the next paint for every changed or inserted element, whatever the throttle does. The harness below has a mutant-checked test for exactly this.
- **Never fight the page's own observers (1.11.3).** Found 2026-11-23: claude.ai froze in Safari (WebContent at 100% CPU for minutes, page scripts never ran again). `sample` of the process: the main thread never left one microtask checkpoint, two `MutationObserver` callbacks taking turns, one in `removeChild`/`insertBefore`, ours in `getComputedStyle(...).getPropertyValue`. claude.ai's message box is a ProseMirror (tiptap) editor, which **rebuilds a paragraph whenever an attribute on it changes** (checked on the live page: setting and removing `data-ifs-probe` on its `<p>` replaced the element, every time). Our probe sets exactly that attribute on every new element at once, so each rebuilt paragraph was probed and rebuilt again, forever. CodeMirror 6 reacts to attribute changes the same way.
  - `IFS.inEditor(el)` (`content-core.js`): inside `[contenteditable]` (not `="false"`) or a `designMode` document. `content-backgrounds.js` never probes, pins or marks such elements: CSS pictures there stay suppressed (not shown; acceptable: editors draw text and `<img>`), and a page's inline `!important` picture is still covered. `<img>` in an editor is still checked: ProseMirror ignores mutations inside leaf nodes (images).
  - General safety net, `IFS.noteObserverCall` / `IFS.calming()`: every observer callback of ours counts itself; 25 calls before a task gets to run = a loop with the page, and for 3 s (doubling, up to 60 s, if it starts again within 10 s) **new** elements are checked from a task 500 ms later (`content-backgrounds.js`) or by the 250 ms scan (`content.js`) instead of synchronously. Hiding is never delayed: a changed `src`, an inline `!important` background, new content in a checked SVG and a video's new source are still handled at once (the first version deferred everything and failed the harness's storm test: an inline `!important` picture would have shown for up to 0.5 s).
  - Measured with a harness (`loop-old/new.html` in the session scratchpad: a fake editor and a fake widget that rebuild an element on any attribute change, capped at 3,000): 1.11.2 hit the cap on both within 4 s; 1.11.3 rebuilds the editor 0 times and the widget about 4–10 times a second with the page responsive (timer lag 5 ms); a `src` swap during the calm spell hid the picture at once and showed the checked one after. Harness `invariants` all pass; `added` 779 style reads/s (762 before).
- **Measure with `scripts/perf/content_script_harness.html`** (usage in its header): real content scripts on a 6,400-element page, scenarios `idle`, `class`, `style`, `added` and `invariants` (a picture is never visible before it is checked, also during a storm). Compare the *counts*, not the milliseconds. Measured against the previous code: idle 9 → 2.5 ms/s with 6× fewer whole-document element visits; class toggling 5,759 → 586 style reads/s and 1,920 → 195 attribute writes/s; inline-style animation 3,304 → 0 reads/s; layout reads from the sweep 1,042 → 0/s; inserting pictures is inherent work (new elements must be read) at 1,198 → 762 reads/s.
- Not measured yet: the per-picture canvas encode on the page's main thread (image-heavy pages), `<video>` frame drawing, inline-SVG rasterising, and what the content scripts cost on an **excluded** site (they still start in every frame, read storage and switch themselves off; reported 2026-11-23: console.cloud.google.com "takes forever to load" with the site excluded — compare with the extension switched off before concluding anything).

### Extension enforcement (macOS)

Safari has no API for an app to turn an extension on, so "enforced" means: **while the extension is off, Safari can't be used.** Once a second, only while Safari or a Safari web app is open (no polling otherwise), the always-on watcher takes one reading from two sources: `SFSafariExtensionManager.getStateOfSafariExtension`, and Safari's own per-profile settings files (`SafariProfileSettings`, next section). `ExtensionGate.combine` merges them: anything wrong in either is `off`; settings fine and the API not saying off is `on` (the API fails on about every other call); settings unreadable is `unknown` even when the API says on (it takes no profile, so it can't vouch for the profiles in use).

- **Two `off` readings in a row** → quit Safari and every Safari web app (`terminate()`, `forceTerminate()` after 2 s) and show a floating notice (top-right corner so it doesn't cover Safari Settings; never takes focus) that names what's wrong ("turned off in the “Mike” profile", "isn't allowed on all websites", "isn't allowed in Private Browsing") with a *Fix in Safari Settings…* button.
- The button opens Safari Settings → Extensions (`SFSafariApplication.showPreferencesForExtension`) and starts a **120 s setup period** (`ExtensionGate.setupDuration`) in which Safari may stay open and the notice counts down. Still off at the end → Safari is closed again. An `on` reading ends the period and hides the notice.
- **An unreadable state fails closed**, but only after 15 readings in a row that were not `on` (`unreadableReadingsToBlock`): the API can fail for a few seconds after login or wake. The notice then says it can't confirm the state, or, when macOS refused to let the watcher read Safari's settings, that it needs **Full Disk Access** (button: *Open Full Disk Access Settings…*).
- All decisions are in `ExtensionGate.swift` and `SafariProfileSettings.swift` (no AppKit). `scripts/test_extension_gate.sh` runs their tests (`macOS/Tests/ExtensionGate/`; plain swiftc, not an Xcode target; the settings reader is tested against a fake Safari folder with the measured `SafariTabs.db` schema). Mutation-checked: skipping the profiles in use, treating a missing `Enabled` as off, letting unreadable settings pass when the API says on, ignoring Private Browsing, denied websites, expiry dates, a permission error, an unlisted profile or the `active_profile_id` fallback each make tests fail.
- **Why not a configuration profile:** Apple's only control over a Safari extension's state is the declaration `com.apple.configuration.safari.extensions.settings` (`State: AlwaysOn`), which needs macOS 15+, a **supervised** enrollment and an MDM; no classic profile payload touches it (`com.apple.NSExtension` can only allow/deny extensions by ID). So the app enforces it itself, as described above.
- No quit item and no way to switch the enforcer off from the app.
- **Duplicate registrations are what made the extension switch itself off between launches (found 2026-11-08).** Every build, from Xcode or `xcodebuild`, in any folder (including other sessions' scratch folders), registers its own copy of the extension under the same ID. `pluginkit -mAv` hides duplicates; `pluginkit -mADv -i FelzyTech.Image-Filter-Service.Extension` shows them. With several copies Safari can resolve the ID to one you didn't switch on, so the extension is off at the next launch, the state API alternates between an answer and `SFErrorNoExtensionFound`, and the Turn On button fails (three copies of 1.5.0 were registered). After building, remove the build's copies — `pluginkit -r <appex>` and `lsregister -u <app>` for every path except `/Applications` — or build under a throwaway bundle ID. The watcher also starts every Safari session from a clean slate (`ExtensionGate.startNewSession`): before, a block left over from one session closed the next one on its first reading, 0.08 s after Safari opened, so the extension could never be read as on. The release pkg guards against this: it is built from a component plist that forbids relocation for the app and the extension (runners older than macOS 27 default to relocatable, which lets the installer update any other copy of the bundle on the Mac instead of `/Applications` — in `PackageInfo` that shows as `<relocate>` containing the bundle ID, and a safe pkg has an empty `<relocate/>`), and its postinstall unregisters every copy of the app and extension except `/Applications` (as the console user; registrations only, never files). CI signs with the same Apple Development identity as a local build (repo secret `MACOS_CERTIFICATE`), so the GitHub release pkg installs the same way a local build does.
- **The state API only works from the app that contains the extension, and only while that copy is the one registered with pluginkit.** From a CLI tool or an unregistered copy it fails with `SFErrorDomain` code 1 (`SFErrorNoExtensionFound`): measured 15/15 failures from an unregistered scratch build, versus a first reading in ~0.3 s and no flapping from a registered app. So **while developing**, an Xcode/xcodebuild build registers its DerivedData copy over `/Applications`' (and may reset the extension's on/off state in Safari — re-tick it), the installed watcher's state API can no longer read the state. With Full Disk Access and readable settings that no longer closes Safari (settings fine + API unknown = `on`); without them it closes Safari after 15 s. Stop it while developing: `launchctl bootout gui/$(id -u)/com.imagefilter.server` (restart: `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.imagefilter.server.plist`). Even from the registered installed app it fails on about every other call (measured with Safari open: `on` and `unknown` alternating once a second; not caused by a second, stale registration of the extension). The enforcer retries a failed read once immediately, and the gate tolerates the rest: one `on` reading (after combining with the settings files) resets everything, and an unreadable reading never cancels a run of `off`.
- Not covered / not verified: during the setup period Safari's other windows aren't covered, so a restored page can show unfiltered pictures for a few seconds; Safari "Add to Dock" web apps are polled like Safari, but their own extension settings weren't found (no `Extensions.plist` in the `com.apple.Safari.WebApp` container) and aren't checked; which profile the state API reports is still unknown (it said "on" while Personal was off — perhaps "on in any profile"). Per-profile gaps: see the next section.
- Debug-only test hooks (not in Release builds — checked, 0 strings in the Release objects): `IFS_ENFORCER_TARGET=<bundle id>` closes that app instead of Safari (e.g. `com.apple.calculator`) and makes *Turn On* skip Safari Settings; `IFS_ENFORCER_STATE_FILE=<path>` reads `on`/`off`/`unknown` from a file; `IFS_ENFORCER_SAFARI_DIR=<path>` reads `SafariTabs.db` and the `Extensions.plist` files from that folder instead of Safari's container (a copy of the real one, or one like the tests' fake). Run the agent as `Image-Filter_Service --start-server-only` and end it with `kill` (before 1.10.0 it had to be `kill -9`: a normal quit stopped the live server, and with no PID file `pkill`ed every gunicorn on the Mac). Test with a copy of the project under a different bundle ID, not the real one.

#### Per-profile settings (`SafariProfileSettings.swift`, added 2026-11-23)

Found 2026-11-23: the extension was off in the "Personal" profile while the state API said "on", so Safari ran unfiltered there. The switch, website access and Private Browsing are per profile; the API takes no profile. So the watcher reads Safari's files directly (all inside `~/Library/Containers/com.apple.Safari/Data/Library/Safari/`; measured on Safari 27.2 / macOS 27.2, undocumented):
- **`SafariTabs.db`** (read-only SQLite, ~0.35 ms per full reading). `bookmarks` rows with `subtype = 2` are the profiles: `external_uuid` is the profile's ID (`DefaultProfile` for Personal, whose `title` is empty), `server_id` its settings folder. `windows` has one row per window: open now **and** the previous session's (closed windows stay, their closing time only inside `extra_attributes`, until the launch after next). The profile is `ProfileUUID` in the `extra_attributes` plist, else `active_profile_id`. Measured with a 100 ms monitor: a new window in another profile was in the table ~0.2 s *before* it appeared on screen. **Private windows are never written there**, and their title carries no profile name.
- **`WebExtensions/Extensions.plist`** (Personal) and **`Profiles/<server_id>/WebExtensions/Extensions.plist`** (every other profile), entry `FelzyTech.Image-Filter-Service.Extension (J97QDPV6YC)`: `Enabled`; `GrantedPermissionOrigins` / `RevokedPermissionOrigins` map origin → expiry date (`4001-01-01` = for good; "All Websites: Allow" is `*://*/*`; "Ask" leaves only per-site grants, as other extensions' entries show); `AllowInPrivateBrowsing` exists only in Personal's file, and is absent for extensions never allowed there.
- **The rule (owner's choice, 2026-11-23: only profiles in use count).** Checked: **Personal always** (private windows can't be seen, and the only Private Browsing setting is Personal's), plus **every profile with a row in `windows`** (so a profile used in the last session still counts during the next one — Safari may reopen its windows). A checked profile is `off` if its `Enabled` is false, `*://*/*` isn't granted (or has expired), or any website is denied; Personal is also `off` without `AllowInPrivateBrowsing = true`. A profile with no window is ignored, even if the extension is off there.
- **Anything not in that shape is "can't confirm" (`unknown`), never "off" and never "fine"**: a missing file, entry, `Enabled` or website key, a value of another type, a window whose profile Safari doesn't list or a folder name with `/`. So a Safari update that changes the format closes Safari after 15 s with the "can't confirm" notice instead of letting it run.
- **Needs Full Disk Access.** Without it every read fails with `EPERM` in 1–15 ms and **no prompt**. Measured with a probe signed like the watcher (team J97QDPV6YC, hardened runtime, not sandboxed, throwaway bundle ID) started by launchd: the container folder, both plists and `SafariTabs.db` (SQLite: "authorization denied") were all refused. So the person switches it on in System Settings → Privacy & Security → Full Disk Access (the notice's button opens that list; the app may have to be added with +), or an MDM pushes a PPPC payload (`SystemPolicyAllFiles`; works on a user-approved, unsupervised enrollment). Until then every Safari session is closed after 15 s with the Full Disk Access notice. **The first version with this check closes Safari until Full Disk Access is granted** — tell the person before it auto-updates.
- Considered and rejected for "in use": window titles ("Personal — page title") need Screen Recording or Accessibility, which are more permissions, and Screen Recording keeps asking again; matching windows reported by the extension itself can't see the profiles where the extension is off.
- **Verified end to end (2026-11-23)** with a harness: the real `ExtensionEnforcer`/`ExtensionGate`/`SafariProfileSettings` sources built `-D DEBUG` with the app target's isolation flags into a signed test app with its own bundle ID and no extension (so nothing registers with pluginkit), started by launchd, `IFS_ENFORCER_TARGET=com.apple.calculator`, state file `on`. Real Safari folder, no Full Disk Access: Calculator closed after 15 s, `unverifiable(noFileAccess)`, notice 412×235 pt. `IFS_ENFORCER_SAFARI_DIR` with a Mike window and the extension off in Mike: closed after 1–2 s, `off([turnedOff("Mike")])`, notice 412×157 pt. All fine: not closed in 20 s. The notice's look wasn't captured (no screen-recording permission in that shell).
- Not verified: the real watcher *with* Full Disk Access (only the denial was measured; the reader was run against this Mac's real files from a shell that has Full Disk Access: Personal and Mike in use, fine) and whether a grant takes effect without restarting the watcher (System Settings may offer *Quit & Reopen*; launchd restarts it); how our own entry looks after choosing "Ask", "Deny" or "Allow for One Day" (inferred from other extensions' entries), and whether switching Private Browsing off writes `false` or removes the key (both count as off); how soon Safari writes `Extensions.plist` after a switch changes (not timed; the state API is still read alongside); whether private windows really run with Personal's extension settings; whether *Fix in Safari Settings…* lands on the right profile's settings (it opens Safari Settings → Extensions).

### Auto-update (macOS)

The Mac app updates itself from this repo's GitHub Releases, **silently**: no window, notice, sound or Dock icon, ever. The only trace is the version in the extension popup (`v1.8.1`) going up. Files: `macOS/App/UpdateConfig.swift` (what is trusted), `UpdateCore.swift` (trust rules, no network), `UpdateService.swift` (check, stage, swap), `UpdateScheduler.swift` (runs inside the always-on watcher), `scripts/update/sign_update.swift` (CI signing tool). iOS is unaffected (App Store/TestFlight).

- **Feed.** `https://github.com/<UpdateConfig.repo>/releases/latest/download/update.json`, plain HTTPS, **no credentials in the app, so the repo must be public** (a private repo answers 404: no update, no harm, logged). Each release carries `Image-Filter-Service-X.Y.Z.zip` (the re-signed app, `ditto`-zipped like the one inside the `.pkg`) and `update.json`; CI step "Build signed update files" makes both, before the tag is pushed.
- **Trust chain (all four must hold, any failure = nothing installed):** (1) `update.json` is an Ed25519-signed envelope (`{format, payload, signature}`); nothing in it is read before the signature verifies against `UpdateConfig.publicKeyBase64`. (2) The signed manifest pins the zip's exact size and SHA-256. (3) The unpacked app must be signed by our team (`anchor apple generic and identifier "<id>" and certificate leaf[subject.OU] = "J97QDPV6YC"`, seal and nested code checked; the Team ID survives yearly certificate renewals, the certificate name would not), have our bundle ID, the version the manifest promised, and a `LSMinimumSystemVersion` this Mac meets; the extension is checked the same way. (4) Only a strictly newer version is ever installed. Downloads and redirects may only touch `github.com`, `*.github.com` and `*.githubusercontent.com` over HTTPS. The staged copy is validated again right before the swap and once more after it (rollback if it fails).
- **When it installs.** Checks run in the background (first 2 min after the watcher starts, then every 6 h, 30 min after a failure). A verified update waits in `~/Library/Application Support/Image-Filter-Service/Updates.noindex/staged/` and is installed only while **no Safari or Safari web app is open** (`UpdateGate`), triggered when the last one quits, at watcher start, or by the 60 s tick. Safari left open for days = the update just waits. The swap is one `renamex_np(RENAME_SWAP)`; if that is refused (see below) it falls back to two renames; the watcher then `launchctl kickstart -k`s itself, so launchd starts the new copy.
- **Dev builds never update themselves:** only a bundle inside `/Applications` or `~/Applications` does (`disabledReason`).
- **The installed bundle must stay exactly as signed.** After a self-update the bundle belongs to the user, so anything that writes into it breaks the code signature (`codesign --verify`: "file added"; found live on 2026-11-10, when the old Python server wrote `Contents/Resources/server/__pycache__`). Nothing that runs from inside the bundle may write there. If `codesign --verify --deep --strict /Applications/Image-Filter_Service.app` ever says "file added", delete the named file.
- **Needs write access to `/Applications`** (an admin user). A standard user can't replace the root-owned app: the install fails with "not writable", is logged, and is retried 3 times, after which that version is left alone (`maxInstallAttempts`); install the `.pkg` instead. The postinstall deliberately does **not** `chown` the app to the user: that would let a non-admin user modify the filter.
- **Root-owned old bundle (installed by the `.pkg`).** The user can neither move nor delete it, so the atomic exchange is refused (errno 13, measured live on 2026-11-10) and the fallback leaves the old copy beside the app as a hidden `/Applications/.Image-Filter_Service.app.replaced-<time>` (not `.app`, so it is not listed or indexed). **Launch Services follows a registered bundle when it is renamed**, so that copy and its extension were registered again a moment AFTER the updater had unregistered them: two registrations of the extension, the trap described above (found live, fixed by hand with `pluginkit -r <appex>` and `lsregister -u <app>`). The updater therefore sweeps (`removeLeftoverRegistrations`) 4 s after the swap, before restarting, and again 20 s after every watcher start. It touches only registrations under the hidden `.replaced-` prefix and its own `Updates.noindex` folder, never other copies (a dev build's registration is left alone). The new bundle belongs to the user, so later updates exchange atomically and delete the old copy. An admin can `sudo rm -rf` the leftover.
- **Never unregisters `/Applications`' extension**: the sweep above matches only the updater's own leftover locations, so the duplicate-registration trap can't be triggered by an update, and `UpdateRegistrations` is unit-tested against the real `pluginkit -mADv` output (installed app and dev builds are never returned).
- **Log and state:** `~/Library/Logs/Image-Filter-Service/update.log`, `Updates.noindex/state.json` (last check, staged version, failed attempts). Look there first.
- **Keys.** Private key: GitHub secret `UPDATE_SIGNING_KEY` and the maintainer's login Keychain (item "Image-Filter-Service update signing key"; **back it up**, GitHub secrets can't be read back). Public key: `UpdateConfig.publicKeyBase64`. CI signs, then verifies against that constant and checks the unzipped app against the production requirement with `codesign -R`, so a secret that doesn't match the constant fails the release before it is tagged. Without the secret the release still ships the `.pkg`, just no update files (warning). To rotate: ship a release (signed with the old key) that contains the new public key, then replace the secret. Losing the key means shipping a new `.pkg` by hand.
- **Rolling it out.** The first version that contains the updater must be installed by `.pkg`; every later one arrives by itself.
- **Tests.** `scripts/test_update.sh` (about 3 s, nothing installed or registered): versions, manifest validation, host policy, the signature (wrong key, forged payload, garbage), and the real `UpdateService` against a local server that redirects like GitHub's CDN: install, fallback swap, read-only old bundle, rollback and the 3-attempt limit, tampered zip, wrong bundle ID, app whose version differs from the manifest, files changed after signing, wrong signing identity, redirect to a foreign host, 404, lock contention, same/older versions. It also checks the production requirement against the installed `/Applications` app (read-only). The verifier was mutation-checked: removing the signature check, the hash check or the code-signature check each makes tests fail.
- **Verified live (2026-11-10, 1.9.2 → 1.9.3, no manual step):** the anonymous check, download, signature/hash/code-signature verification and staging; install deferred while Safari was open; install about 1 s after Safari quit, through the two-rename fallback; the watcher restarted onto the new copy. **Not verified:** whether macOS ever shows an "App Management" prompt when an app replaces its own bundle in `/Applications` (none was reported, but it was not asked); that Safari loads the new extension cleanly after the swap (`lsregister -f` is run); the atomic-exchange path on a live install (the first update of a user-owned bundle will be the first run); the GitHub download path under heavy redirect/CDN variation (only the one live fetch).

### Serverless (since 1.10.0, 2026-11-23)

Until 1.9.x the Mac sent every picture to a local Python server (Flask + gunicorn, MediaPipe's TFLite model on the CPU, port 10000), which the watcher started while Safari was open, from a virtualenv it built from Homebrew's `python3` and `pip install`ed at first launch. Now the Mac runs the same in-extension engine as iPhone/iPad (*The filter engine* below). Owner's decision, after the server turned out to be the cause of most failures:
- it wasn't running yet when Safari opened, crashed or hung, and was slow under a page-load burst (it ran at `nice 10`, CPU only: MediaPipe's Metal delegate crashes in its Python build on macOS); a missing Homebrew Python or a failed `pip install` meant no filter at all;
- it listened on `0.0.0.0:10000` with open CORS and a URL-download endpoint, so other devices on the network, and any website, could use it;
- its downloads (python-requests from this Mac's IP, claiming to be Safari) made Cloudflare sites challenge the real browser (see *Bot checks*);
- Python could write `__pycache__` into a user-owned bundle and break its signature.

**Measured in real Safari 27.2 on this Mac** (2026-11-23; the engine in a plain page, GPU delegate; test set: 14 photos of people, 6 graphics with no people, 4 composites with small people/banners/grid, 8 avatars of 64–128 px, 2 video frames; compared with the server's own `detect_skin` on the same ≤768 px JPEGs):
- the same filter decision as the server on **34/34** pictures;
- share of the server's skin pixels the engine also greys: photos 97.4–99.9%, composites 93.6–97.9%, avatars 88.8–96.5%; extra pixels ≤0.8% of the picture (one 64 px avatar 6.5%);
- time per picture: people photos median 112 ms (max 174), graphics 24 ms; a burst of 30 pictures 2.7 s; engine load 0.6 s, reload 0.6 s;
- memory of the page holding the engine: ~290 MB after loading, ~230 MB idle, ~350 MB after the burst, ~160 MB after `release()` (the server: ~260 MB warm, 320–340 MB peak).

What changed:
- **Removed:** `server/` (app, start scripts, review-log tools), `runtime.txt`, the CI steps that downloaded the model and copied the server into the bundle, the native `ensureServer` message and its handler code, the watcher's server start/stop/health checks and first-launch setup, the iOS extension's local-network permission (it was for a LAN server).
- **Kept for compatibility:** the LaunchAgent label `com.imagefilter.server` and the watcher's `--start-server-only` argument (installed agents use them), the popup's old `checkServer` action name (answered like `checkFilter`). Stale storage keys `serverUrl` and `engine` are deleted when the background loads.
- **Cleanup on installed Macs:** the watcher removes what the server left (`LegacyServerCleanup` in `AppDelegate.swift`: stops a server still running, identified by its own PID file and checked to be gunicorn; deletes `~/Library/Application Support/Image-Filter-Service/venv`, `gunicorn.pid` and `~/Library/Caches/Image-Filter-Service/pycache`). It never touches the logs (`~/Library/Logs/Image-Filter-Service/server*.log` stay as history), `Updates.noindex` or `review/`. The installer's postinstall stops an old server the same way (PID file only; it used to `pkill` every `gunicorn … app:app` on the Mac).
- **Gone with the server:** the opt-in review log (thumbnails of every greyed picture, `review_report.py`). An existing `review/` folder is left alone; nothing writes to it.
- **Verified live (2026-11-23, 1.10.0 installed in /Applications, Safari 27.2):** a probe page (6 pictures with people, 4 graphics, `data:` SVG `<img>`s, inline SVGs incl. one with `:class`/`@click`, a CSS background) opened as Safari launched: all 15 checked within 1.1 s of page load, 6/6 people greyed, 4/4 graphics unchanged, icons shown within 0.4 s; nothing listening on port 10000. The first watcher start removed the old server's venv (382 MB), PID file and bytecode cache. Probe: a page whose script reads each element's `data-filter-processed` and whether its `src` became a `blob:` URL, and posts the result to a local server.
- **Watch out when testing:** the extension's on/off switch is per Safari profile (Personal's settings are the top-level `…/Safari/WebExtensions/Extensions.plist`; other profiles are under `…/Safari/Profiles/<UUID>/WebExtensions/`). Before the per-profile check (*Extension enforcement* → *Per-profile settings*) the watcher read "on" while the extension was off in "Personal"; it now reads those files, but only with Full Disk Access, and only for profiles in use. A page that shows every picture unfiltered means the extension isn't running in that profile, not that the engine let them through.
- **Not verified yet:** the engine inside the extension's background page over a long session on the Mac (memory over hours, Safari unloading the idle page and the reload delay), video on the Mac, very image-heavy pages (the engine checks one picture at a time), and whether it runs on the GPU there (the popup's Activity screen shows the delegate).

### The filter engine (`Shared/Extension/ondevice/`)

```
content.js  →  ≤768px JPEG  →  background.js  →  ondevice/engine.js (MediaPipe WASM, GPU→CPU fallback)
content.js  ←  skin mask (run-length encoded)  ←  background.js
content.js paints grey over the full-res image it already decoded (paintFilteredImage)
```

- **Files.** `engine.js` (ours) plus `@mediapipe/tasks-vision` 0.10.32 (`vision_bundle.js` = the package's `.mjs`, SIMD `vision_wasm_internal.*` only) and `selfie_multiclass_256x256.tflite`; ~27 MB. An *explicit folder* of the `Shared/Extension` synchronized group (like `_locales` and `images`), so both appexes get `Resources/ondevice/`. (It lived in `iOS/Extension/ondevice/`, iOS only, until 1.10.0.) Re-create/upgrade with `scripts/fetch_ondevice_assets.sh` (pinned, sha256-checked); test in Safari on the Mac and in the iOS Simulator after an upgrade.
- **Categories:** **2 = body-skin**, **3 = face-skin** are greyed; 0 (background), 1 (hair), 4 (clothes), 5 (others) are left alone.
- **Tiled detection** (the old server's `detect_skin`, reproduced exactly; sizes use Python's round-half-to-even). The model only sees 256×256, so one pass over a whole photo misses people who are small in the frame (measured on test composites: 14–29% of skin greyed in group shots, ~75% in 4:1 banners; 0% of a 4:1 banner / 6:1 strip with the old single pass on iOS). The engine works on a ≤768 px copy and segments the whole image (≤320 px) **plus overlapping square tiles** (384 px; smaller for small images, as tall as the image for banners; none for images ≤300 px, thin strips <64 px, or >16 tiles). Skin = max over passes of P(body-skin)+P(face-skin) > 0.3 (deliberately below argmax), then dilated ~2 px (elliptical, radius = longest side / 384); a picture is filtered when ≥0.1% of its pixels are skin. Result: ~98–100% of skin covered in every test layout, at the cost of 1–2% of non-skin pixels (hair/collar edges) also greyed. One deliberate difference from the server: tiles >256 px are shrunk to the model's 256 on a canvas before inference (same masks, 10–20% faster). Mask addition happens on the GPU with one readback (self-tested at warm-up, falls back to CPU readback).
- **Modes:** `'full'` (default; pictures: 5–9 inferences for a typical 512–768 px image), `'fast'` (whole frame + frame-height tiles, ~3 passes for 16:9; used for video frames), `'single'`. Every inference costs about the same whatever the input size, so latency is set by the number of passes. Input is 768 px (`SEG_MAX`, duplicated in `content.js` and `content-core.js`); smaller inputs lose small people (512: crowds 83/59%, 320: a 6:1 strip passes unfiltered). Grey 128 is blended with the bilinear-upscaled mask (canvas `drawImage` of the mask does the upscale + blend).
- **Colour gate for tiny images** (`notSkinColour`, `SKIN_COLOUR_GATE_MAX` = 256). Images ≤256 px (avatars, icons, logos — the model must stretch them 4–8×) hallucinate a head in any round blob with space under it: a 40 px blue letter avatar ("D" on a disc, Google's default account icon) came back 50–70% grey. On those images, pixels whose colour no skin has are zeroed before thresholding: saturated blue/cyan/green/violet (hue 80°–290°, S>0.55), near-white (S≤0.08, V≥0.92) and vivid bright red/orange/pink (S>0.8, V>0.6), grown 1 px (OpenCV's 8-bit HSV rules; pixels read back from the whole-image canvas, which is the work copy at that size). Browns, tans, pinks and greys are deliberately *not* gated (black-and-white and tinted photos must still be filtered), so a dark-brown disc is still greyed. Measured on 1,120 synthetic letter avatars (server): blue/purple/green/teal 13–16% grey → ~0%, red/orange/crimson 5–22% → 0.3–4%; real photos ≤256 px lost 0.7% of the flagged pixels (hair edges, a flower — no face); nothing above 256 px changes. In the iOS Simulator's Safari on 112 letter avatars: blue discs 16.7% → 0.0% grey, avatars >1% grey 38% → 13%. Rejected: sharper upscaling (bicubic made it worse), a higher threshold for small images (helps a little, costs real recall).
- **Tuning notes** (accuracy audit on the server, same model and maths: 31 no-person images, 112 avatars, 13 people images): threshold 0.3→0.5 trades 4.6 points of coverage for a third fewer false alarms, and the rest are confident (≥0.9) mistakes on smooth warm artwork; upscale-small-images and flip-merge variants each moved recall and false positives together — no free win inside this model.
- **Loading.** `background.js` loads it with `import(browser.runtime.getURL('ondevice/engine.js'))` (the background stays a classic script) and starts loading as soon as the page wakes (the content scripts' initial `getConfig` wakes it), plus one warm-up inference — the first real inference otherwise costs ~1.5 s. It releases the engine after `ENGINE_IDLE_MS` with nothing to check: 60 s on iOS (memory), 10 min on the Mac (spares the ~0.6 s reload after every pause in browsing). Safari may unload the idle background page anyway. If the engine fails to load, checks fail closed; when a later load works, every tab gets `filterReady` and retries what failed.
- GPU (WebGL2) delegate measured ~6× faster than CPU in the iOS Simulator (27 vs 159 ms median, identical masks); `engine.js` falls back to CPU if GPU init or a later segment call fails. Safari on the Mac: GPU.
- If content.js can't read an image's pixels (cross-origin without CORS), it sends only the URL and the background downloads + filters it itself (`filterUrl`), through Safari — this needs the extension to be allowed on the image's host ("All Websites → Allow"). Without it those images stay hidden.
- Manifest `content_security_policy.extension_pages` adds `'wasm-unsafe-eval'` (required to compile WebAssembly). iOS deployment target is 16.4 (WASM SIMD).
- Failures return `{success: true, error, fallback: true}` → `failed` → the image stays hidden and is retried.
- **Measuring:** a plain web page in Safari (Mac or Simulator) can import `ondevice/vision_bundle.js` and `engine.js` directly (same WebKit as the extension) — much faster to iterate than rebuilding the app. Image state (`data-filter-processed`, inline opacity) is readable from page JS, which makes a probe page easy. The 2026-11-23 Mac measurement compared the engine's masks with the old server's `detect_skin` (`git show 44ed345:server/app.py`).

### iOS (iPhone / iPad)

The same project also builds for iOS: targets **Image-Filter_Service iOS** (UIKit host app, shows setup steps only) and **Image-Filter_Service iOS Extension**. They live in `iOS/App/` and `iOS/Extension/`; the macOS targets in `macOS/App/` and `macOS/Extension/`. The web extension (manifest, JS, popup, images, `_locales`) is **shared**: `Shared/Extension/` is a synchronized folder in *both* extension targets (its contents land flat in each appex's `Resources/`; `_locales`, `images` and `ondevice` are explicit folders). The platform folders hold only native code, Info.plists and entitlements. Edit extension JS once and both platforms get it. Target, product and scheme names are unchanged from before the move (`Image-Filter_Service`, `Image-Filter_Service Extension`, `… iOS`, `… iOS Extension`) — the release workflow and installer depend on them.

**Memory (iOS).** iOS gives Safari's per-page and extension processes much less than the phone's RAM, and caps a page's total canvas memory (past it, new canvases fail → pictures would stay hidden). Measured in the simulator with `footprint` (simulator processes carry ~200 MB of overhead; compare deltas):
- The engine is most of the cost: the background page with MediaPipe loaded is ~115–145 MB above a blank web process, ~210 MB at its load peak — even with no checks run, so it's the runtime + model, not the work. Streaming the model in (`modelAssetBuffer` reader) was measured *worse* (+66 MB); the CPU delegate too (+50 MB). `background.js` releases the engine after 60 s idle on iOS (`engine.release()`), and Safari unloads the idle background page anyway (process gone after ~90 s); the next page reloads it (~0.3–0.6 s, warm-up starts as the page opens).
- Pages: no measurable overhead on an ordinary page (8 large photos); on a 5,000-element page with 171 pictures, +~45 MB at rest and +~140 MB at the loading peak.
- Rules that keep it there: every temporary canvas is shrunk to 0×0 as soon as it's used (`IFS.releaseCanvas`, also in engine.js); our decoded copies of images are dropped after a check (`image.src = ''`); filtered pictures are `blob:` URLs in bounded caches (`IFS.boundedCache`, 200 entries) whose evicted URLs are revoked when nothing on the page shows them (`IFS.urlInUse`); `background.js` `responseCache` is capped (300); video frames reuse their canvases (work canvas ≤768 = the engine input, so no per-frame copy); at most 4 `<img>` + 3 other checks are in flight per page (the engine works one image at a time — more in flight only holds more decoded copies).
- Not verified on a real iPhone: the extension background page's actual limit is undocumented. Check on a device (Safari → Develop → the iPhone → the extension's background page → Timelines → Memory) on image-heavy sites and with video.

- Build/run: `xcodebuild -project Image-Filter_Service.xcodeproj -scheme "Image-Filter_Service iOS" -destination 'generic/platform=iOS Simulator' build`. The simulator shares the Mac's network (so test pages served from `127.0.0.1` work). After install, enable it from Safari's page menu → *Manage Extensions*, then grant site access.
- Version numbers: the iOS targets use the same `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` text as macOS, so `.github/scripts/bump_version.py` (a global regex replace) keeps all four targets in step.

## Extension Configuration (Stored in `browser.storage.local`)

| Key | Default | Description |
|---|---|---|
| `isEnabled` | `true` | Whether filtering is active. **iOS only** — on the Mac there is no off switch: the background ignores any stored or requested `false` (and rewrites a stale stored `false` to `true`), and `content.js` ignores it unless `platform === 'ios'` |
| `platform` | — | `'ios'` or `'mac'`, written by `background.js` every time it loads. `content.js` reads storage directly and uses this to decide whether `isEnabled` counts; missing/unknown fails closed (always on) |
| `excludedSites` | `[]` | Hostnames not filtered (lowercase, no `www.`; an entry covers its subdomains) |
| `passwordRecord` | — | Mac only: `{salt, hash, iterations}` — PBKDF2-SHA256, 200k iterations, random 16-byte salt (base64). Never sent to the popup or content scripts (`getConfig` returns only `passwordSet`) |
| `passwordFailures`, `passwordLockedUntil` | `0` | Wrong-guess counter and lockout end time (persisted, so restarting the background page doesn't clear a lockout) |
| `pageWorldVersion` | — | Which definition of the `page-world.js` registration is current (`PAGE_WORLD_VERSION` in `background.js`); a lower or missing number makes the background replace the registration once |
| `serverUrl`, `engine` | — | Left over from before 1.10.0 (the Mac's server URL, server vs on-device engine). Nothing reads them; the background deletes them when it loads |

**Excluded websites.** The popup has a *Filter this website* switch for the active tab (main screen) and an *Excluded websites* screen (add/remove). `background.js` normalises the list (`normalizeSite`: URL/`www.`/`*.` stripped) and broadcasts it with `updateConfig`; `content.js` combines it with `isEnabled` (`applyEnabled`) and drives the existing disable path, so an excluded page looks exactly like one with filtering switched off (revealed live, no reload). Matching uses the **top-level page's** host (`location.ancestorOrigins` in frames): frames on an excluded site are unfiltered, an excluded site framed inside another page is still filtered, and a frame that can't tell its top page filters. Switching a site back on removes every entry that covers it (parent domains too). `page-world.js` can't read storage, so `content.js` tells it (event `ifs-release-page-world`) once filtering is off for the page (excluded, or switched off on iOS) and it puts the browser's own functions back (shadow roots, video fullscreen/PiP) for the rest of that page: nothing of the extension is left for a site's bot check to trip over. Switching filtering back on live filters again, but without those two protections until the page is reloaded. A page could dispatch the event itself; it would only gain native fullscreen and closed shadow roots for itself.

**macOS lock-down (no off switch, password to exclude).** Both are enforced in `background.js` (`isLockedDown()` = platform is not iOS), not just in the popup; iPhone/iPad are unchanged.
- *Always on.* The popup shows "Always on" and no switch (`#enableSwitch` is only un-hidden when `config.platform === 'ios'`). `updateConfig` ignores `isEnabled` on the Mac, and `loadConfig` forces `config.isEnabled = true`.
- *Password to exclude a website.* Any `updateConfig` whose `excludedSites` **adds** a site (the "Filter this website" switch going off, or the Add form on the Excluded websites screen) must carry `password`, checked against `passwordRecord`; otherwise nothing in the request is applied and the reply is `{success: false, error: 'wrong-password' | 'locked' | 'no-password'}`. **Removing** a site (filtering again) never asks. With no password set, excluding is refused (fail closed) until one is set (`setPassword`; first password needs no auth, changing it needs the current one; min 6 characters). The popup's *Password* card (Excluded websites screen) does it, and excluding with no password set opens that prompt itself and then excludes using the password just made. Five wrong guesses in a row lock checking for 5 minutes (a correct password during the lock is refused too). The popup only collects the password (`openDialog` in `popup.js`; `<input type=password>` in an in-page dialog, because `prompt()` can't mask input).
- *Nothing to point elsewhere.* There is no server, so there is no address a different "server" that answers "no skin" could be put at (that loophole was why the Mac's server URL was fixed before 1.10.0).

Users set these via the popup UI (toolbar icon).

**Popup (`popup.html` / `popup.css` / `popup.js`, shared by Mac and iOS).** Three screens, one visible at a time: *main* (status card, *Filter this website* switch, rows to the other two), *Excluded websites* (add form, list with Remove, and on the Mac the Password card), *Activity* (the four counters, engine/speed facts, Clear cache). Back buttons return to main and give focus back to the row that opened the screen.
- **Status card** (`#hero`, `data-state`): `checking` (grey) until the background answers → `on` (green) / `error` (red, "Filter not running… pictures stay hidden": `checkFilter` said the engine couldn't load, or `getConfig` failed) / `off` (amber, iOS only; the iOS off switch lives on this card). On iOS the engine check is skipped while filtering is off, because `checkFilter` loads the whole engine.
- **Prompts** are the in-page `#dialog` (`openDialog`: password fields, or none for a plain confirmation like Clear cache; `inert` on `#app` while open; the popup is a fixed 420px so the tallest prompt fits without the popover resizing). `confirm()`/`prompt()` aren't used.
- **Sizing:** every size is a CSS variable (`--row-height`, `--switch-width`…); the `@supports (-webkit-touch-callout: none)` block (iOS only) overrides them for the full-width sheet (16px text so iOS doesn't zoom inputs, 44px+ targets). Mac popover: 340×420px on **every** screen (`--screen-height`; long lists scroll inside `.screen-body`): a popover that resizes while a screen changes or a prompt opens is what made the animations jump.
- **Animations (found glitchy in real Safari):** the screen change is a slide (`slide-forward` from the right, `slide-back` from the left; `transform`/`opacity` only; `will-change`/`backface-visibility` only while the class is on, which `showScreen` removes on `animationend` *and* on a 400 ms timer, because with Reduce Motion there is no animation and so no event). The popup opens with `body.loading` (header only, body hidden, 0.5 s cap, CSS fallback after 1 s) and reveals once config, site, stats and the engine check are in, so it never flashes "Checking…"/"None"/"No website open" and then swaps them. The status card has no colour transition. Switch: stays on while a password prompt is open (it only goes off once the exclusion is saved).
- **Focus rings only after a key press** (`body.keyboard`, set on the first `keydown`): Safari focuses the first control when the popup opens, which drew a stray blue outline on the first row. Rows highlight with an inset tint (an outline's square corners get clipped by the rounded card); screen headings take script focus and never show a ring.
- **Testing without Safari:** `browser` doesn't exist in a plain page, so use a throwaway harness: a mock `browser.runtime.sendMessage` answering `getConfig` (`platform`, `isEnabled`, `excludedSites`, `passwordRequired`, `passwordSet`), `getStats`, `checkFilter`, `clearCache`, `updateConfig` (refuses added sites without the right `password` on the Mac, like `background.js`) and `setPassword`, plus `browser.tabs.query` and `runtime.getManifest`, loading the real `popup.js`/`popup.css` over http. Chromium doesn't match `-webkit-touch-callout`, so to preview the iPhone sheet swap that `@supports` for `@media all` in a copy of the CSS. In the Browser pane, CSS transitions don't advance while the pane is in the background: call `document.getAnimations().forEach(a => a.finish())` before judging a screenshot's colours.

## Key Design Decisions

- **No caching** — cache is intentionally disabled in both `content.js` and `background.js`. Comments explain this: base64 responses are unique per processing run, so caching would serve stale data.
- **Images stay hidden on failure** — `data-filter-processed="failed"` means the image is never revealed. This is by design for religious compliance.
- **A picture is visible only while it shows exactly the pixels that were checked** — every kind (verified frame-by-frame in the iOS Simulator with page-side probe pages: `<img>`/`<picture>`, backgrounds incl. pseudo-elements, SVG, shadow DOM, video — all 0 leaked frames; keep it that way). For `<img>`:
  - The hide rule (`hideAllStyle`) applies to every `<img>` not marked `true`: `opacity: 0` + `visibility: hidden`, `!important`, ID-level specificity (`:not(#_)` ×3) so page CSS can't override, and `transition: none` so re-hiding is instant (a fade-out would show a swapped-in picture). Only revealing fades in, via inline style. `ensureHideStyle()` puts the stylesheet back if a page removes it (observer + scan).
  - Approval pins the element (`pinSource`): `data-filter-approved` = the exact URL, `srcset` removed and `<picture>` `<source>`s disabled (originals kept in `data-filter-srcset`, restored on disable). Without this, `<picture>` sources override the filtered `img.src` (the original was shown — real bug, found by test) and media queries/rotation could switch to an unchecked picture.
  - Reveal happens in `tryReveal()` only once the element is `complete` and `currentSrc` equals the approved URL (on load/error, plus every scan) — never on `decode()` timing, which can settle for the previous picture.
  - Any change to what an image displays — `src`/`srcset` (including inline `data:` photos), a `<source>` srcset, a new `<source>` — calls `recheck()`: hidden immediately, re-checked. Our own pinning is recognised via `data-filter-approved` and ignored.
  - Each check is a numbered round (`newRound`/`isCurrent`); results from an older round are dropped, so a slow result can't pin an image the page has since changed.
  - **Backgrounds** (`content-backgrounds.js`): `IFS.BG_CSS` suppresses `background-image`/`list-style-image`/`border-image-source` on *every* element and `::before`/`::after`. The page's intended value is read by a **probe** (set `data-ifs-probe`, which lifts the suppression, read `getComputedStyle`, remove it — one synchronous task, never across a paint), its pictures checked, and the approved value **pinned** inline `!important` (pseudo-elements: per-element rule via `IFS.setPseudoRule`). The page's own inline values are remembered (restored for probes and on disable). A page's inline `!important` beats the suppression, so it is covered in the same microtask. Pictures in `content: url()` aren't covered by the suppression; that pseudo-element is hidden by a per-element rule when detected. Re-probes: mutations (added nodes at once, class/id/inline-style changes bounded and throttled, see *Keeping the extension light*); stylesheet loads/resize/`load` and a safety-net sweep (only when something happened, near the viewport, skipping recently probed elements) in 200-element chunks with a rendered frame between (a full read of 5,000 elements is ~0.4 s). Hover-only pictures are never pinned (skipped in sweeps) — they stay suppressed.
  - **SVG** (`content-elements.js`): `<img src=*.svg>` goes through content.js like any image (SVG decode: Safari's `createImageBitmap` rejects SVG, so the background/engine fall back to an `<img>`). Inline `<svg>` is rasterised (computed paint inlined, `<use href=#…>` targets brought along, `<foreignObject>` dropped) and checked; identical markup is checked once (icon sets). Clean → live SVG (`true`); skin → its children hidden and the filtered raster set as its background (`raster`). New child elements hide it until re-checked; attribute changes re-check while it stays visible. `<svg><image>` is checked like an `<img>`.
  - **Shadow DOM**: `page-world.js` forces roots open and adopts a stopgap sheet at `attachShadow` time; the core finds roots (host tagged `data-ifs-shadow`, plus walking added subtrees), adopts its constructed sheets (replacing the stopgap), observes the root, and hands its images to every module.
  - **Video** (`content-video.js`): the `<video>` stays at opacity 0 (NOT `visibility:hidden` — WebKit pauses muted autoplay then). An overlay `<canvas>` (next sibling, `data-ifs-overlay`) draws a frame only after *that frame* is checked and greyed (`checkCanvas(..., { mode: 'fast' })`), so motion can't expose skin. Poster checked first. `playsinline`, PiP/AirPlay disabled; native fullscreen/PiP refused. **A video that can't be filtered plays unfiltered (owner's decision, 2026-11-08; the one exception to "fails closed" — images still stay hidden).** `Player.releaseVideo` marks the video `data-ifs-unfiltered` (the hide rule `video:not([data-ifs-unfiltered])` in `IFS.ELEMENT_CSS` and the `page-world.js` copy stops matching), hides the overlay, puts the page's own `playsinline`/PiP/AirPlay attributes back, and `page-world.js` lets that video use fullscreen/PiP. Two cases: (1) **frames unreadable** (cross-origin without CORS, or DRM — `checkCanvas` throws `SecurityError` from `toDataURL`): unfiltered, no more checks, until a new source (`emptied` / `src` change) removes the marker and starts again hidden + filtered. (2) **Checks failing** (the engine won't load: `r.failed`, or a thrown timeout): after `FAIL_GRACE_MS` (2 s) of failures in a row **while the video plays** (a paused video stays hidden; one success resets the run) it is released, then probed every `PROBE_MS` (2 s); the first check that works calls `resumeFiltering` (marker off, presentation locked again, native fullscreen/PiP left, overlay drawn in the same task). A check that hangs (20 s timeout) keeps the video hidden until it times out. Disabling filtering removes the marker. Verified with a harness (same- vs cross-origin no-CORS video, mock filter up/down/flaky/throwing, pause/play, src swaps, disable/enable, fullscreen/PiP gating); not yet tried in real Safari / on an iPhone. Measured ~6.8 fps for one video on the simulator (tiled 'fast'); two videos share the engine.
  - Filtered outputs are encoded with `canvas.toBlob` → `blob:` URL (`IFS.canvasToUrl`), not `toDataURL`: a synchronous JPEG encode plus 0.3–0.6 MB strings in inline styles stalled long pages.
  - Checks time out after 20 s (`withTimeout`) so a lost background reply can't leave a picture hidden forever; failures retry with back-off. That includes `<img>` (`content.js`, since 1.11.1): before, a check whose reply never came kept its slot forever, and four such checks (`MAX_CONCURRENT`) stopped every other picture on the page from being checked (harness: 4 hanging replies → 2 more pictures never started; now all 6 shown after 23 s).
  - **Not covered:** canvas-drawn images (maps, editors), `<object>`/`<embed>` SVG documents' external images, external `<use>` sprites inside inline SVG (vector icons), closed *declarative* shadow roots, vector-only changes inside an approved inline SVG made by attribute animation (re-checked, not hidden), and any page the extension isn't running on — on iOS sites it isn't allowed on, and a page that loads while Safari is (re)starting the extension right after an install/update (measured: video visible ~0.4 s). `content: url()` introduced by a stylesheet that loads later can show until the next probe.
- **Pixels in, mask out (not URL redirects)** — Unlike MB Filter (which uses `declarativeNetRequest` redirects), this extension reads each picture's pixels on the page and checks them in the background page. Intentional: Safari's `declarativeNetRequest` support is limited, and only pixels can be checked. Where the pixels come from: (1) the page's own already-decoded `<img>` if readable (same-origin/CORS) — no second download; (2) a CORS copy (`data:` and `blob:` pictures are always readable this way); (3) if the site doesn't allow CORS, the background downloads it itself (`engine.filterUrl`: host permissions, Safari's cache/cookies, decodes AVIF/HEIC). If that fails too, the picture stays hidden.
- **Concurrent request limit** — `MAX_CONCURRENT = 4` `<img>` checks in flight per frame in `content.js` (and 3 other checks in `content-core.js`); the engine checks one picture at a time, so more would only hold more decoded copies. Images beyond the limit are picked up on the next 250 ms scan.
- **Bundle ID** — `FelzyTech.Image-Filter-Service` used in native messaging and app launch coordination.
- **Background waits for stored config (`configReady`)** — Safari unloads the idle background page (aggressively on iOS), and the message that wakes it is handled *before* `browser.storage` has been read. Every handler that depends on config (`filterImage`, `getConfig`, `updateConfig`, `checkFilter`) awaits `configReady`; otherwise the first requests after each wake would ignore the disabled toggle (iOS) or the excluded list. (Found by testing in the iOS Simulator, when there was still a server URL to get wrong.)
- **Failed images are retried by the content script** — `retryFailedImages` in `content.js` re-queues `failed` images every 5 s, doubling up to 60 s while they keep failing. Inline SVG, `<object>`/`<embed>` and CSS pictures keep their own back-off (5 s → 60 s per element). On `filterReady` (the background's engine loaded after a failed load) **every** module retries at once (`retryNow`, called by `content-core.js`; before 2026-11-23 only `<img>` listened, so a toolbar of SVG icons stayed blank for up to a minute after the filter was back). Images stay hidden throughout.
- **Server down or slow (fixed 2026-11-23, then removed with the server in 1.10.0)** — console.cloud.google.com's top bar was missing. The server was only down for seconds at a time, but the old code turned that into minutes of blank pages: SVG/CSS pictures waited out their own back-off after it was back (6.0 s measured after a 12 s outage), everything was sent at once with an 8 s timeout that counted gunicorn's backlog and each failure was resent twice (100 icons: 227 requests, last icon after 35 s), and every failing request asked the app to start the server (`host.log`: ~170 bootstrap launches). 1.9.7 fixed those (request queue, waiting for a starting server, `serverOnline` to every module); 1.10.0 removed the server, and with it this whole class of failure. The `retryNow` plumbing remains, driven by `filterReady`.
- **Pictures that failed every time (fixed 2026-11-23, 1.9.7)** — some pictures stayed hidden with the server running, because their check could never succeed: about 1,100 of the 2,100 errors in `server.log` since 2026-11-10. Both causes below were in the content scripts, so they matter for the engine too.
  - `content.js` passed a page's `data:` image URLs to the server unchanged, and the server only reads base64 raster images: every `data:image/svg+xml,…`, `;utf8,…` or `;base64` SVG (the usual way to inline an icon) failed with "Incorrect padding", "cannot identify image file" or "list index out of range". Now a `data:` URL goes through the canvas like any other picture (it is always readable); the engine path always did.
  - An inline SVG with an attribute name XML doesn't allow (Alpine/Vue `:class`, `@click`, `x-on:click`, `v-bind:…`: allowed in HTML) couldn't be rasterised: the copy failed to load, every time. `styledCopy` now drops such attributes (`dropNonXmlAttributes`); they never change the picture.
  - Not a cause: the "No image data or URL provided" lines in `server.log` were not pictures but the extension's `checkServer` HEAD request, which the route handed to its POST branch (harmless log noise).
  - Measured in the harness (real background + content scripts, the server running): old code never showed 4 of 7 test pictures (3 kinds of `data:` SVG `<img>`, the Alpine/Vue SVG); new code showed all 7 within 0.1 s, against both a fake server and the real server code.
  - Not found: why console.cloud.google.com's top bar specifically was missing (it needs a sign-in; its icons were fetched, then not shown, while the server was up at 20:52–20:53 on 2026-11-22). The causes above fit, but it wasn't reproduced on that page.
