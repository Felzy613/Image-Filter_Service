# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A two-component system: a **Safari extension** (Manifest v3) that intercepts web images and sends them for filtering, and a **Python Flask server** that uses MediaPipe to detect and grey-out human skin regions. The use case is religious compliance — all images must be filtered before being shown.

## Architecture

```
Web Page → content.js (canvas → base64) → background.js → Flask server (MediaPipe)
                                                                     ↓
Web Page ← content.js (replaces img.src) ← background.js ← filtered base64 JPEG
```

Images are hidden immediately when a page loads (`opacity: 0`), processed through the server, then revealed. **Images remain hidden if the server is unavailable** — this is intentional for religious compliance, not a bug.

### Extension (Safari / Xcode)

- **Content scripts** (all in `Shared/Extension/`, loaded in this order, sharing `globalThis.__ifs` in the isolated world):
  - `content-core.js` — hide-until-checked CSS for the document **and every shadow root**, shadow-root registry + observer, `IFS.checkUrl` (picture by URL, cached per page) / `IFS.checkCanvas` (pixels we drew: video frames, inline-SVG rasters), engine selection, enable/disable fan-out.
  - `content.js` — `<img>`/`<picture>` (canvas → base64 → background; `MutationObserver` + 250 ms scan for lazy images). Exposes `__ifs.img` so the core can hand it images inside shadow roots.
  - `content-elements.js` — inline `<svg>` (rasterised with computed styles, checked; shown live if clean, else the filtered raster replaces it), `<svg><image>`, `<input type=image>`, `<object>`/`<embed>` images.
  - `content-backgrounds.js` — CSS `background-image` / `list-style-image` / `border-image`, on elements and `::before`/`::after` (incl. `content: url()`).
  - `content-video.js` — `<video>`: never shown; an overlay canvas draws only checked frames.
- **`page-world.js`** — runs in the page's own JS world (registered by `background.js` via `scripting.registerContentScripts({ world: 'MAIN' })`; Safari ignores `"world"` in the manifest). Forces every shadow root open + adopts a stopgap hide sheet at creation; blocks page scripts from native video fullscreen / Picture in Picture.
- **`Shared/Extension/background.js`** — Receives from content script, POSTs to Flask server, returns filtered base64 to content script. Manages `browser.storage.local` for persisted config (server URL, enabled state). On connection failure, calls `browser.runtime.sendNativeMessage` to trigger server auto-start.
- **`macOS/Extension/SafariWebExtensionHandler.swift`** — Handles native messages from the extension. On `{command: "ensureServer"}`, launches the host app with `--start-server-only`.
- **`macOS/App/AppDelegate.swift`** — On launch, checks if port 10000 is reachable. If not, spawns `server/start_server.py` (in the bundle: `Contents/Resources/server/start_server.py`) as a subprocess. In `--start-server-only` mode it stays alive as a watcher and keeps the server running only while Safari **or a Safari "Add to Dock" web app** is open. Web apps are separate processes with bundle ID `com.apple.Safari.WebApp.<UUID>` that load the extension, so they must count as Safari.
- **`macOS/App/ExtensionEnforcer.swift`, `ExtensionGate.swift`** — keep the extension switched on (see *Extension enforcement* below). `AppDelegate` starts the enforcer in `--start-server-only` mode only; the normal app window is unchanged.

### Extension enforcement (macOS)

Safari has no API for an app to turn an extension on, so "enforced" means: **while the extension is off, Safari can't be used.** The always-on watcher polls `SFSafariExtensionManager.getStateOfSafariExtension` once a second, only while Safari or a Safari web app is open (no polling otherwise):

- **Two `off` readings in a row** → quit Safari and every Safari web app (`terminate()`, `forceTerminate()` after 2 s) and show a floating notice (top-right corner so it doesn't cover Safari Settings; never takes focus) with a *Turn On in Safari Settings…* button.
- The button opens Safari Settings → Extensions (`SFSafariApplication.showPreferencesForExtension`) and starts a **120 s setup period** (`ExtensionGate.setupDuration`) in which Safari may stay open and the notice counts down. Still off at the end → Safari is closed again. An `on` reading ends the period and hides the notice.
- **An unreadable state fails closed**, but only after 15 readings in a row that were not `on` (`unreadableReadingsToBlock`): the API can fail for a few seconds after login or wake. The notice then says it can't confirm the state.
- All decisions are in `ExtensionGate.swift` (no AppKit). `scripts/test_extension_gate.sh` runs its tests (`macOS/Tests/ExtensionGate/`; plain swiftc, not an Xcode target).
- **Why not a configuration profile:** Apple's only control over a Safari extension's state is the declaration `com.apple.configuration.safari.extensions.settings` (`State: AlwaysOn`), which needs macOS 15+, a **supervised** enrollment and an MDM; no classic profile payload touches it (`com.apple.NSExtension` can only allow/deny extensions by ID). So the app enforces it itself, as described above.
- No quit item and no way to switch the enforcer off from the app.
- **Duplicate registrations are what made the extension switch itself off between launches (found 2026-11-08).** Every build, from Xcode or `xcodebuild`, in any folder (including other sessions' scratch folders), registers its own copy of the extension under the same ID. `pluginkit -mAv` hides duplicates; `pluginkit -mADv -i FelzyTech.Image-Filter-Service.Extension` shows them. With several copies Safari can resolve the ID to one you didn't switch on, so the extension is off at the next launch, the state API alternates between an answer and `SFErrorNoExtensionFound`, and the Turn On button fails (three copies of 1.5.0 were registered). After building, remove the build's copies — `pluginkit -r <appex>` and `lsregister -u <app>` for every path except `/Applications` — or build under a throwaway bundle ID. The watcher also starts every Safari session from a clean slate (`ExtensionGate.startNewSession`): before, a block left over from one session closed the next one on its first reading, 0.08 s after Safari opened, so the extension could never be read as on. The release pkg guards against this: it is built from a component plist that forbids relocation for the app and the extension (runners older than macOS 27 default to relocatable, which lets the installer update any other copy of the bundle on the Mac instead of `/Applications` — in `PackageInfo` that shows as `<relocate>` containing the bundle ID, and a safe pkg has an empty `<relocate/>`), and its postinstall unregisters every copy of the app and extension except `/Applications` (as the console user; registrations only, never files). CI signs with the same Apple Development identity as a local build (repo secret `MACOS_CERTIFICATE`), so the GitHub release pkg installs the same way a local build does.
- **The state API only works from the app that contains the extension, and only while that copy is the one registered with pluginkit.** From a CLI tool or an unregistered copy it fails with `SFErrorDomain` code 1 (`SFErrorNoExtensionFound`): measured 15/15 failures from an unregistered scratch build, versus a first reading in ~0.3 s and no flapping from a registered app. So **while developing**, an Xcode/xcodebuild build registers its DerivedData copy over `/Applications`' (and may reset the extension's on/off state in Safari — re-tick it), the installed watcher can no longer read the state, and it closes Safari after 15 s. Stop it while developing: `launchctl bootout gui/$(id -u)/com.imagefilter.server` (restart: `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.imagefilter.server.plist`). Even from the registered installed app it fails on about every other call (measured with Safari open: `on` and `unknown` alternating once a second; not caused by a second, stale registration of the extension). The enforcer retries a failed read once immediately, and the gate tolerates the rest: one `on` reading resets everything, and an unreadable reading never cancels a run of `off`.
- Not covered / not verified: the API reports only the on/off switch, not whether the extension has access to all websites (Safari → Settings → Extensions → Edit Websites…); extension state is per Safari profile and the API takes no profile, so which profile it reports is unchecked; during the setup period Safari's other windows aren't covered, so a restored page can show unfiltered pictures for a few seconds.
- Debug-only test hooks (not in Release builds — checked, 0 strings in the Release objects): `IFS_ENFORCER_TARGET=<bundle id>` closes that app instead of Safari (e.g. `com.apple.calculator`) and makes *Turn On* skip Safari Settings; `IFS_ENFORCER_STATE_FILE=<path>` reads `on`/`off`/`unknown` from a file. Run the agent as `Image-Filter_Service --start-server-only` and end it with `kill -9` (SIGKILL skips `applicationWillTerminate`, which would stop the live server). Test with a copy of the project under a different bundle ID, not the real one.

### Auto-update (macOS)

The Mac app updates itself from this repo's GitHub Releases, **silently**: no window, notice, sound or Dock icon, ever. The only trace is the version in the extension popup (`v1.8.1`) going up. Files: `macOS/App/UpdateConfig.swift` (what is trusted), `UpdateCore.swift` (trust rules, no network), `UpdateService.swift` (check, stage, swap), `UpdateScheduler.swift` (runs inside the always-on watcher), `scripts/update/sign_update.swift` (CI signing tool). iOS is unaffected (App Store/TestFlight).

- **Feed.** `https://github.com/<UpdateConfig.repo>/releases/latest/download/update.json`, plain HTTPS, **no credentials in the app, so the repo must be public** (a private repo answers 404: no update, no harm, logged). Each release carries `Image-Filter-Service-X.Y.Z.zip` (the re-signed app, `ditto`-zipped like the one inside the `.pkg`) and `update.json`; CI step "Build signed update files" makes both, before the tag is pushed.
- **Trust chain (all four must hold, any failure = nothing installed):** (1) `update.json` is an Ed25519-signed envelope (`{format, payload, signature}`); nothing in it is read before the signature verifies against `UpdateConfig.publicKeyBase64`. (2) The signed manifest pins the zip's exact size and SHA-256. (3) The unpacked app must be signed by our team (`anchor apple generic and identifier "<id>" and certificate leaf[subject.OU] = "J97QDPV6YC"`, seal and nested code checked; the Team ID survives yearly certificate renewals, the certificate name would not), have our bundle ID, the version the manifest promised, and a `LSMinimumSystemVersion` this Mac meets; the extension is checked the same way. (4) Only a strictly newer version is ever installed. Downloads and redirects may only touch `github.com`, `*.github.com` and `*.githubusercontent.com` over HTTPS. The staged copy is validated again right before the swap and once more after it (rollback if it fails).
- **When it installs.** Checks run in the background (first 2 min after the watcher starts, then every 6 h, 30 min after a failure). A verified update waits in `~/Library/Application Support/Image-Filter-Service/Updates.noindex/staged/` and is installed only while **no Safari or Safari web app is open** (`UpdateGate`), triggered when the last one quits, at watcher start, or by the 60 s tick. Safari left open for days = the update just waits. The swap is one `renamex_np(RENAME_SWAP)`; if that is refused (see below) it falls back to two renames; the watcher then stops the server and `launchctl kickstart -k`s itself, so launchd starts the new copy.
- **Dev builds never update themselves:** only a bundle inside `/Applications` or `~/Applications` does (`disabledReason`).
- **The installed bundle must stay exactly as signed.** After a self-update the bundle belongs to the user, so Python could write `Contents/Resources/server/__pycache__` into it, which breaks the code signature (`codesign --verify`: "file added"; found live on 2026-11-10 right after the first self-update; the root-owned `.pkg` install had hidden it because the write simply failed). `server/start_server.py` therefore sets `PYTHONPYCACHEPREFIX=~/Library/Caches/Image-Filter-Service/pycache` for the server (guarded by `scripts/test_update.sh`). Nothing that runs from inside the bundle may write there. If `codesign --verify --deep --strict /Applications/Image-Filter_Service.app` ever says "file added", delete the named file.
- **Needs write access to `/Applications`** (an admin user). A standard user can't replace the root-owned app: the install fails with "not writable", is logged, and is retried 3 times, after which that version is left alone (`maxInstallAttempts`); install the `.pkg` instead. The postinstall deliberately does **not** `chown` the app to the user: that would let a non-admin user modify the filter.
- **Root-owned old bundle (installed by the `.pkg`).** The user can neither move nor delete it, so the atomic exchange is refused (errno 13, measured live on 2026-11-10) and the fallback leaves the old copy beside the app as a hidden `/Applications/.Image-Filter_Service.app.replaced-<time>` (not `.app`, so it is not listed or indexed). **Launch Services follows a registered bundle when it is renamed**, so that copy and its extension were registered again a moment AFTER the updater had unregistered them: two registrations of the extension, the trap described above (found live, fixed by hand with `pluginkit -r <appex>` and `lsregister -u <app>`). The updater therefore sweeps (`removeLeftoverRegistrations`) 4 s after the swap, before restarting, and again 20 s after every watcher start. It touches only registrations under the hidden `.replaced-` prefix and its own `Updates.noindex` folder, never other copies (a dev build's registration is left alone). The new bundle belongs to the user, so later updates exchange atomically and delete the old copy. An admin can `sudo rm -rf` the leftover.
- **Never unregisters `/Applications`' extension**: the sweep above matches only the updater's own leftover locations, so the duplicate-registration trap can't be triggered by an update, and `UpdateRegistrations` is unit-tested against the real `pluginkit -mADv` output (installed app and dev builds are never returned).
- **Log and state:** `~/Library/Logs/Image-Filter-Service/update.log`, `Updates.noindex/state.json` (last check, staged version, failed attempts). Look there first.
- **Keys.** Private key: GitHub secret `UPDATE_SIGNING_KEY` and the maintainer's login Keychain (item "Image-Filter-Service update signing key"; **back it up**, GitHub secrets can't be read back). Public key: `UpdateConfig.publicKeyBase64`. CI signs, then verifies against that constant and checks the unzipped app against the production requirement with `codesign -R`, so a secret that doesn't match the constant fails the release before it is tagged. Without the secret the release still ships the `.pkg`, just no update files (warning). To rotate: ship a release (signed with the old key) that contains the new public key, then replace the secret. Losing the key means shipping a new `.pkg` by hand.
- **Rolling it out.** The first version that contains the updater must be installed by `.pkg`; every later one arrives by itself.
- **Tests.** `scripts/test_update.sh` (about 3 s, nothing installed or registered): versions, manifest validation, host policy, the signature (wrong key, forged payload, garbage), and the real `UpdateService` against a local server that redirects like GitHub's CDN: install, fallback swap, read-only old bundle, rollback and the 3-attempt limit, tampered zip, wrong bundle ID, app whose version differs from the manifest, files changed after signing, wrong signing identity, redirect to a foreign host, 404, lock contention, same/older versions. It also checks the production requirement against the installed `/Applications` app (read-only). The verifier was mutation-checked: removing the signature check, the hash check or the code-signature check each makes tests fail.
- **Verified live (2026-11-10, 1.9.2 → 1.9.3, no manual step):** the anonymous check, download, signature/hash/code-signature verification and staging; install deferred while Safari was open; install about 1 s after Safari quit, through the two-rename fallback; the watcher restarted onto the new copy. **Not verified:** whether macOS ever shows an "App Management" prompt when an app replaces its own bundle in `/Applications` (none was reported, but it was not asked); that Safari loads the new extension cleanly after the swap (`lsregister -f` is run); the atomic-exchange path on a live install (the first update of a user-owned bundle will be the first run); the GitHub download path under heavy redirect/CDN variation (only the one live fetch).

### Flask Server (`server/app.py`)

- Endpoint: `POST /api/filter-image` — accepts `{imageData: "<base64>", imageUrl: "<url>"}`, returns `{success, filteredImageUrl, filtered, containsSkin, skinRatio}`.
- Endpoint: `GET /api/filter-image?url=<url>` — downloads and returns a filtered image directly (not used by the extension currently).
- MediaPipe model (`selfie_multiclass_256x256.tflite`) is downloaded lazily to `server/models/` on first use.
- Categories filtered: **2 = body-skin**, **3 = face-skin**. Categories 0 (background), 1 (hair), 4 (clothes), 5 (others) are left untouched.
- **Tiled detection (`detect_skin`).** The model only sees 256×256, so one pass over a whole photo misses people who are small in the frame (measured on test composites: 14–29% of skin greyed in group shots, ~75% in 4:1 banners). The server works on a ≤768px copy and segments the whole image (≤320px) **plus overlapping square tiles** (384px; smaller for small images, as tall as the image for banners; none for images ≤300px, thin strips <64px, or >16 tiles). Skin = max over passes of P(body-skin)+P(face-skin) > `SKIN_PROB_THRESHOLD` (0.3, deliberately below argmax), then dilated ~2px. Result: ~98–100% of skin covered in every test layout, no person-containing scene missed (old: 2), at the cost of 1–2% of non-skin pixels (hair/collar edges) also greyed.
- **Colour gate for tiny images (`_not_skin_colour`, `SKIN_COLOUR_GATE_MAX`).** Images ≤256px (avatars, icons, logos — the model must stretch them 4–8×) hallucinate a head in any round blob with space under it: a 40px blue letter avatar ("D" on a disc, Google's default account icon) came back 50–70% grey, and the live log showed 33–128px images filtered 30–40% of the time. On those images, pixels whose colour no skin has are zeroed before thresholding: saturated blue/cyan/green/violet (hue 80°–290°, S>0.55), near-white (S≤0.08, V≥0.92) and vivid bright red/orange/pink (S>0.8, V>0.6), grown 1px. Browns, tans, pinks and greys are deliberately *not* gated (black-and-white and tinted photos must still be filtered), so a dark-brown disc is still greyed. Measured on 1,120 synthetic letter avatars: blue/purple/green/teal 13–16% grey → ~0%, red/orange/crimson 5–22% → 0.3–4%; on real photos ≤256px it removed 0.7% of the flagged pixels (hair edges, a flower — no face) and nothing above 256px changes (bit-identical). Rejected: sharper upscaling (bicubic made it worse), a higher threshold for small images (helps a little, costs real recall). Mirrored in the iOS on-device engine (`notSkinColour` in `engine.js`, same rules on OpenCV's 8-bit HSV; keep `SKIN_COLOUR_GATE_MAX` in step).
- **Review log (opt-in; `_review_submit`, `server/review_report.py`).** Accuracy work needs real examples of mistakes, not just synthetic ones (the letter-avatar bug was found from a screenshot plus the live log). While the folder `~/Library/Application Support/Image-Filter-Service/review/` (or `REVIEW_LOG_DIR`) **exists**, every picture the server greys is also saved there as a ≤384px JPEG thumbnail with a line in `index.jsonl` (time, size, skin share, site *host* only). Create the folder to turn it on, delete it to turn it off — checked per request, no restart. Privacy by construction: only the *greyed* result is saved (what the browser already showed), never the original; images with no skin are never saved; no URL path/query. Requests only shrink + queue the picture (bounded queue, drops when full); one daemon thread hashes, encodes and writes (same greyed picture → same file, so repeats are saved once), and prunes to `REVIEW_LOG_MAX` (500) newest. Measured: 11 ms median per request with it on or off. `python3 server/review_report.py` builds `index.html` in that folder: click the pictures that should *not* have been greyed, "Copy list", send it back (marks persist in the browser). It only sees false positives — misses are never saved by design. Tuning notes from the accuracy audit (31 no-person images, 112 avatars, 13 people images; coverage vs the full-size run, not hand-labelled): threshold 0.3→0.5 trades 4.6 points of coverage for a third fewer false alarms and the rest are confident (≥0.9) mistakes on smooth warm artwork; upscale-small-images and flip-merge variants each moved recall and false positives together — no free win inside this model.
- **Inference: TFLite directly, 2 interpreters × 4 threads (memory-tuned).** The server does not use MediaPipe's Python `ImageSegmenter`: it calls the TFLite C API + XNNPACK delegate exported by mediapipe's own `libmediapipe.dylib` via `ctypes` (no extra dependency), with MediaPipe's pre/post-processing reproduced exactly — masks are bit-identical to the `ImageSegmenter` version (0 of 41.3M pixels differ on the test scenes). `SEG_INTERPRETERS` (default 2) interpreters, each with `SEG_INTERPRETER_THREADS` (default 4) XNNPACK threads, share one read-only model mapping; a queue lends each interpreter to one thread at a time; tiles of one image run in parallel. Memory: ~97 MB is the Python/numpy/OpenCV/Flask baseline, plus ~80 MB per interpreter (mostly its 256×256 activation arena) → ~260 MB warm / ~320–340 MB peak, vs ~1 GB for the earlier 8 MediaPipe segmenters. Trade-off chosen by the user: page-load bursts ~35% slower than the 1 GB setup (roughly the original single-pass server's speed), single images about the same; `SEG_INTERPRETERS=3` ≈ +80 MB for ~10% off the old 1 GB speed. Tied to the TFLite symbols in mediapipe 0.10.32 (pinned) — re-check on upgrade. Rejected: one shared XNNPACK engine (serializes: 56 vs 151 img/s), XNNPACK weight cache (crashes on this model), FP16 (≈17 MB/interpreter saved but 0.017% of mask pixels change), `MallocSpaceEfficient=1` (numpy import fails randomly). The Metal GPU delegate crashes in MediaPipe's Python build on macOS — stay on CPU.
- `SKIN_RATIO_THRESHOLD` defaults to `0.001` (0.1% skin pixels triggers filtering).
- Errors return `success: true` + `error` so the page isn't broken; `background.js` treats any `error` as **fail closed** (`fallback: true` → image stays hidden, content.js retries with backoff). Before this, such responses were passed on as "no skin" and the image was revealed unchecked.
- URL downloads (last resort — see background fetch below) apply EXIF orientation, so photos come back upright, and use a keep-alive `requests.Session`.

### iOS (iPhone / iPad)

The same project also builds for iOS: targets **Image-Filter_Service iOS** (UIKit host app, shows setup steps only) and **Image-Filter_Service iOS Extension**. They live in `iOS/App/` and `iOS/Extension/`; the macOS targets in `macOS/App/` and `macOS/Extension/`. The web extension (manifest, JS, popup, images, `_locales`) is **shared**: `Shared/Extension/` is a synchronized folder in *both* extension targets (its contents land flat in each appex's `Resources/`; `_locales` and `images` are explicit folders). The platform folders hold only native code, Info.plists, entitlements and (iOS) `ondevice/`. Edit extension JS once and both platforms get it. Target, product and scheme names are unchanged from before the move (`Image-Filter_Service`, `Image-Filter_Service Extension`, `… iOS`, `… iOS Extension`) — the release workflow and installer depend on them.

**On-device filtering (iOS default, no server).** `background.js` has two engines, chosen by `config.engine`: `'server'` (POST to `serverUrl`, the macOS path) and `'device'`. `'device'` exists only on iOS (`resolveEngine()` forces `'server'` elsewhere) and is the only engine on iOS: `resolveEngine()` takes no setting, it returns `'device'` on iOS and `'server'` elsewhere (the popup's *Filter on this device* switch and Server URL field were removed, so a stored `'server'` can't leave a phone on an address it can't reach).

```
content.js  →  ≤768px JPEG  →  background.js  →  ondevice/engine.js (MediaPipe WASM, GPU→CPU fallback)
content.js  ←  skin mask (run-length encoded)  ←  background.js
content.js paints grey over the full-res image it already decoded (paintFilteredImage)
```

- `iOS/Extension/ondevice/` (explicit folder → appex `ondevice/`, iOS only): `engine.js` (ours) plus `@mediapipe/tasks-vision` 0.10.32 (`vision_bundle.js` = the package's `.mjs`, SIMD `vision_wasm_internal.*` only) and the same `selfie_multiclass_256x256.tflite` the server uses. ~28 MB. Re-create/upgrade with `scripts/fetch_ondevice_assets.sh` (pinned, sha256-checked); keep the version in step with `mediapipe` in `server/requirements.txt` so phone and Mac segment identically.
- `engine.js` mirrors the server's **tiled detection** (`detect_skin`/`_tiles`/`_skin_probability` in `server/app.py`): ≤768px work copy, whole image + overlapping tiles, P(body-skin)+P(face-skin) > 0.3 merged by max, elliptical dilation, filter at ≥0.1%. Measured against the server on the same input: 95–99.9% of the server's skin pixels covered on every test image except a crowd of ~70px faces (80%); the old single pass covered 0% of a 4:1 banner / 6:1 strip. One deliberate difference: tiles >256px are shrunk to the model's 256 before inference (same masks, 10–20% faster). Mask addition happens on the GPU with one readback (self-tested at warm-up, falls back to CPU readback). Modes: `'full'` (default; pictures), `'fast'` (whole frame + frame-height tiles, ~3 passes for 16:9; used for video frames), `'single'`. Cost ≈ 27–30 ms per pass on the simulator GPU: a large photo is ~200 ms (vs ~27 ms single-pass); 8 large photos fully filtered ≈ 1.8–2.0 s uncached. Device input is 768px (`SEG_MAX`, duplicated in `content.js` and `content-core.js`); smaller inputs lose small people (512: crowds 83/59%, 320: a 6:1 strip passes unfiltered). Grey 128 is blended with the bilinear-upscaled mask (canvas `drawImage` of the mask does the upscale + blend). It also mirrors the server's **colour gate** for images ≤256px (`notSkinColour`; pixels read back from the whole-image canvas, which is the work copy at that size). Measured in the iOS Simulator's Safari (GPU delegate) on 112 letter avatars + real photos: blue-disc avatars 16.7% → 0.0% grey, avatars >1% grey 38% → 13%, real photos ≤256px within 0.5% of before, larger images identical.
- `background.js` loads it with `import(browser.runtime.getURL('ondevice/engine.js'))` (background stays a classic script) and starts loading as soon as the page wakes (content.js's initial `getConfig` wakes it), plus one warm-up inference — the first real inference otherwise costs ~1.5 s.
- GPU (WebGL2) delegate measured ~6× faster than CPU in the simulator (27 vs 159 ms median, identical masks); `engine.js` falls back to CPU if GPU init or a later segment call fails.
- If content.js can't read an image's pixels (cross-origin without CORS), it sends only the URL and the background downloads + filters it itself (`filterUrl`) — this needs the extension to be allowed on the image's host, hence "All Websites → Allow" in the setup steps. Without it those images stay hidden.
- Manifest `content_security_policy.extension_pages` adds `'wasm-unsafe-eval'` (required to compile WebAssembly). iOS deployment target is 16.4 (WASM SIMD).
- Failures return the server-failure contract (`fallback: true`) → `failed` → image stays hidden and is retried.
- Measuring: a plain web page in the simulator's Safari can import `ondevice/vision_bundle.js` directly (same WebKit as the extension) — much faster to iterate than rebuilding the app. Image state (`data-filter-processed`, inline opacity) is readable from page JS, which makes a probe page easy.

**Memory (iOS).** iOS gives Safari's per-page and extension processes much less than the phone's RAM, and caps a page's total canvas memory (past it, new canvases fail → pictures would stay hidden). Measured in the simulator with `footprint` (simulator processes carry ~200 MB of overhead; compare deltas):
- The engine is most of the cost: the background page with MediaPipe loaded is ~115–145 MB above a blank web process, ~210 MB at its load peak — even with no checks run, so it's the runtime + model, not the work. Streaming the model in (`modelAssetBuffer` reader) was measured *worse* (+66 MB); the CPU delegate too (+50 MB). `background.js` releases the engine after 60 s idle (`engine.release()`), and Safari unloads the idle background page anyway (process gone after ~90 s); the next page reloads it (~0.3–0.6 s, warm-up starts as the page opens).
- Pages: no measurable overhead on an ordinary page (8 large photos); on a 5,000-element page with 171 pictures, +~45 MB at rest and +~140 MB at the loading peak.
- Rules that keep it there: every temporary canvas is shrunk to 0×0 as soon as it's used (`IFS.releaseCanvas`, also in engine.js); our decoded copies of images are dropped after a check (`image.src = ''`); filtered pictures are `blob:` URLs in bounded caches (`IFS.boundedCache`, 200 entries) whose evicted URLs are revoked when nothing on the page shows them (`IFS.urlInUse`); `background.js` `responseCache` is capped (300); video frames reuse their canvases (work canvas ≤768 = the engine input, so no per-frame copy); with the on-device engine at most 4 `<img>` + 3 other checks are in flight per page (the engine works one image at a time — more in flight only holds more decoded copies).
- Not verified on a real iPhone: the extension background page's actual limit is undocumented. Check on a device (Safari → Develop → the iPhone → the extension's background page → Timelines → Memory) on image-heavy sites and with video.

**No server engine on iOS any more.** The `'server'` engine is Mac-only: the popup's switch and Server URL field are gone and `resolveEngine()` always picks `'device'` on iOS, so the server branches in `background.js` are unreachable there. An iPhone can't run the Python server and `127.0.0.1` is the phone itself (a hosted or LAN server was the only option; the iOS extension `Info.plist` still sets `NSAllowsLocalNetworking` for plain-http LAN servers). A separate iOS app hosting a local server doesn't work — iOS suspends it once Safari is in front. The iOS native handler is a no-op; native auto-start only happens on macOS with a localhost `serverUrl` (`canAutoStartLocalServer`, `shouldPollLocalServer`).

- Build/run: `xcodebuild -project Image-Filter_Service.xcodeproj -scheme "Image-Filter_Service iOS" -destination 'generic/platform=iOS Simulator' build`. The simulator shares the Mac's network (so `127.0.0.1` test servers work). After install, enable it from Safari's page menu → *Manage Extensions*, then grant site access.
- Version numbers: the iOS targets use the same `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` text as macOS, so `.github/scripts/bump_version.py` (a global regex replace) keeps all four targets in step.

## Extension Configuration (Stored in `browser.storage.local`)

| Key | Default | Description |
|---|---|---|
| `serverUrl` | `http://127.0.0.1:10000/api/filter-image` | Full API endpoint URL. No popup field (removed); iOS always filters on the device and ignores it. On the Mac it is fixed: the background ignores any stored or requested value and rewrites a stale stored one back to the default (`DEFAULT_SERVER_URL`) |
| `isEnabled` | `true` | Whether filtering is active. **iOS only** — on the Mac there is no off switch: the background ignores any stored or requested `false` (and rewrites a stale stored `false` to `true`), and `content.js` ignores it unless `platform === 'ios'` |
| `platform` | — | `'ios'` or `'mac'`, written by `background.js` every time it loads. `content.js` reads storage directly and uses this to decide whether `isEnabled` counts; missing/unknown fails closed (always on) |
| `excludedSites` | `[]` | Hostnames not filtered (lowercase, no `www.`; an entry covers its subdomains) |
| `passwordRecord` | — | Mac only: `{salt, hash, iterations}` — PBKDF2-SHA256, 200k iterations, random 16-byte salt (base64). Never sent to the popup or content scripts (`getConfig` returns only `passwordSet`) |
| `passwordFailures`, `passwordLockedUntil` | `0` | Wrong-guess counter and lockout end time (persisted, so restarting the background page doesn't clear a lockout) |

**Excluded websites.** The popup has a *Filter this website* switch for the active tab (main screen) and an *Excluded websites* screen (add/remove). `background.js` normalises the list (`normalizeSite`: URL/`www.`/`*.` stripped) and broadcasts it with `updateConfig`; `content.js` combines it with `isEnabled` (`applyEnabled`) and drives the existing disable path, so an excluded page looks exactly like one with filtering switched off (revealed live, no reload). Matching uses the **top-level page's** host (`location.ancestorOrigins` in frames): frames on an excluded site are unfiltered, an excluded site framed inside another page is still filtered, and a frame that can't tell its top page filters. Switching a site back on removes every entry that covers it (parent domains too). `page-world.js` can't read storage, so video fullscreen/PiP stays blocked on excluded sites (same as when globally disabled).

**macOS lock-down (no off switch, password to exclude).** Both are enforced in `background.js` (`isLockedDown()` = platform is not iOS), not just in the popup; iPhone/iPad are unchanged.
- *Always on.* The popup shows "Always on" and no switch (`#enableSwitch` is only un-hidden when `config.platform === 'ios'`). `updateConfig` ignores `isEnabled` on the Mac, and `loadConfig` forces `config.isEnabled = true`.
- *Password to exclude a website.* Any `updateConfig` whose `excludedSites` **adds** a site (the "Filter this website" switch going off, or the Add form on the Excluded websites screen) must carry `password`, checked against `passwordRecord`; otherwise nothing in the request is applied and the reply is `{success: false, error: 'wrong-password' | 'locked' | 'no-password'}`. **Removing** a site (filtering again) never asks. With no password set, excluding is refused (fail closed) until one is set (`setPassword`; first password needs no auth, changing it needs the current one; min 6 characters). The popup's *Password* card (Excluded websites screen) does it, and excluding with no password set opens that prompt itself and then excludes using the password just made. Five wrong guesses in a row lock checking for 5 minutes (a correct password during the lock is refused too). The popup only collects the password (`openDialog` in `popup.js`; `<input type=password>` in an in-page dialog, because `prompt()` can't mask input).
- *Fixed local server.* The Mac has no Server URL option (the popup has no Server URL field at all); `background.js` always uses `DEFAULT_SERVER_URL` there. This closes the loophole where pointing the extension at a server that answers "no skin" would bypass filtering.

Users set these via the popup UI (toolbar icon), except `serverUrl` and `engine`, which have no UI.

**Popup (`popup.html` / `popup.css` / `popup.js`, shared by Mac and iOS).** Three screens, one visible at a time: *main* (status card, *Filter this website* switch, rows to the other two), *Excluded websites* (add form, list with Remove, and on the Mac the Password card), *Activity* (the four counters, engine/speed facts, Clear cache). Back buttons return to main and give focus back to the row that opened the screen.
- **Status card** (`#hero`, `data-state`): `checking` (grey) until the background answers → `on` (green) / `error` (red, "Filter not running… pictures stay hidden": `checkServer` said not connected, or `getConfig` failed) / `off` (amber, iOS only; the iOS off switch lives on this card). On iOS the engine check is skipped while filtering is off, because `checkServer` loads the whole on-device engine.
- **Prompts** are the in-page `#dialog` (`openDialog`: password fields, or none for a plain confirmation like Clear cache; `inert` on `#app` while open; the popup is a fixed 420px so the tallest prompt fits without the popover resizing). `confirm()`/`prompt()` aren't used.
- **Sizing:** every size is a CSS variable (`--row-height`, `--switch-width`…); the `@supports (-webkit-touch-callout: none)` block (iOS only) overrides them for the full-width sheet (16px text so iOS doesn't zoom inputs, 44px+ targets). Mac popover: 340×420px on **every** screen (`--screen-height`; long lists scroll inside `.screen-body`): a popover that resizes while a screen changes or a prompt opens is what made the animations jump.
- **Animations (found glitchy in real Safari):** the screen change is a slide (`slide-forward` from the right, `slide-back` from the left; `transform`/`opacity` only; `will-change`/`backface-visibility` only while the class is on, which `showScreen` removes on `animationend` *and* on a 400 ms timer, because with Reduce Motion there is no animation and so no event). The popup opens with `body.loading` (header only, body hidden, 0.5 s cap, CSS fallback after 1 s) and reveals once config, site, stats and the engine check are in, so it never flashes "Checking…"/"None"/"No website open" and then swaps them. The status card has no colour transition. Switch: stays on while a password prompt is open (it only goes off once the exclusion is saved).
- **Focus rings only after a key press** (`body.keyboard`, set on the first `keydown`): Safari focuses the first control when the popup opens, which drew a stray blue outline on the first row. Rows highlight with an inset tint (an outline's square corners get clipped by the rounded card); screen headings take script focus and never show a ring.
- **Testing without Safari:** `browser` doesn't exist in a plain page, so use a throwaway harness: a mock `browser.runtime.sendMessage` answering `getConfig` (`platform`, `engine`, `isEnabled`, `excludedSites`, `passwordRequired`, `passwordSet`), `getStats`, `checkServer`, `clearCache`, `updateConfig` (refuses added sites without the right `password` on the Mac, like `background.js`) and `setPassword`, plus `browser.tabs.query` and `runtime.getManifest`, loading the real `popup.js`/`popup.css` over http. Chromium doesn't match `-webkit-touch-callout`, so to preview the iPhone sheet swap that `@supports` for `@media all` in a copy of the CSS. In the Browser pane, CSS transitions don't advance while the pane is in the background: call `document.getAnimations().forEach(a => a.finish())` before judging a screenshot's colours.

## Key Design Decisions

- **No caching** — cache is intentionally disabled in both `content.js` and `background.js`. Comments explain this: base64 responses are unique per processing run, so caching would serve stale data.
- **Images stay hidden on failure** — `data-filter-processed="failed"` means the image is never revealed. This is by design for religious compliance.
- **A picture is visible only while it shows exactly the pixels that were checked** — every kind (verified frame-by-frame in the iOS Simulator with page-side probe pages: `<img>`/`<picture>`, backgrounds incl. pseudo-elements, SVG, shadow DOM, video — all 0 leaked frames; keep it that way). For `<img>`:
  - The hide rule (`hideAllStyle`) applies to every `<img>` not marked `true`: `opacity: 0` + `visibility: hidden`, `!important`, ID-level specificity (`:not(#_)` ×3) so page CSS can't override, and `transition: none` so re-hiding is instant (a fade-out would show a swapped-in picture). Only revealing fades in, via inline style. `ensureHideStyle()` puts the stylesheet back if a page removes it (observer + scan).
  - Approval pins the element (`pinSource`): `data-filter-approved` = the exact URL, `srcset` removed and `<picture>` `<source>`s disabled (originals kept in `data-filter-srcset`, restored on disable). Without this, `<picture>` sources override the filtered `img.src` (the original was shown — real bug, found by test) and media queries/rotation could switch to an unchecked picture.
  - Reveal happens in `tryReveal()` only once the element is `complete` and `currentSrc` equals the approved URL (on load/error, plus every scan) — never on `decode()` timing, which can settle for the previous picture.
  - Any change to what an image displays — `src`/`srcset` (including inline `data:` photos), a `<source>` srcset, a new `<source>` — calls `recheck()`: hidden immediately, re-checked. Our own pinning is recognised via `data-filter-approved` and ignored.
  - Each check is a numbered round (`newRound`/`isCurrent`); results from an older round are dropped, so a slow result can't pin an image the page has since changed.
  - **Backgrounds** (`content-backgrounds.js`): `IFS.BG_CSS` suppresses `background-image`/`list-style-image`/`border-image-source` on *every* element and `::before`/`::after`. The page's intended value is read by a **probe** (set `data-ifs-probe`, which lifts the suppression, read `getComputedStyle`, remove it — one synchronous task, never across a paint), its pictures checked, and the approved value **pinned** inline `!important` (pseudo-elements: per-element rule via `IFS.setPseudoRule`). The page's own inline values are remembered (restored for probes and on disable). A page's inline `!important` beats the suppression, so it is covered in the same microtask. Pictures in `content: url()` aren't covered by the suppression; that pseudo-element is hidden by a per-element rule when detected. Re-probes: mutations (style/class/id, added nodes) synchronously; stylesheet loads/resize/`load` and a 10 s near-viewport safety sweep in 200-element chunks with a rendered frame between (a full read of 5,000 elements is ~0.4 s). Hover-only pictures are never pinned (skipped in sweeps) — they stay suppressed.
  - **SVG** (`content-elements.js`): `<img src=*.svg>` goes through content.js like any image (SVG decode: Safari's `createImageBitmap` rejects SVG, so the background/engine fall back to an `<img>`). Inline `<svg>` is rasterised (computed paint inlined, `<use href=#…>` targets brought along, `<foreignObject>` dropped) and checked; identical markup is checked once (icon sets). Clean → live SVG (`true`); skin → its children hidden and the filtered raster set as its background (`raster`). New child elements hide it until re-checked; attribute changes re-check while it stays visible. `<svg><image>` is checked like an `<img>`.
  - **Shadow DOM**: `page-world.js` forces roots open and adopts a stopgap sheet at `attachShadow` time; the core finds roots (host tagged `data-ifs-shadow`, plus walking added subtrees), adopts its constructed sheets (replacing the stopgap), observes the root, and hands its images to every module.
  - **Video** (`content-video.js`): the `<video>` stays at opacity 0 (NOT `visibility:hidden` — WebKit pauses muted autoplay then). An overlay `<canvas>` (next sibling, `data-ifs-overlay`) draws a frame only after *that frame* is checked and greyed (`checkCanvas(..., { mode: 'fast' })`), so motion can't expose skin. Poster checked first. `playsinline`, PiP/AirPlay disabled; native fullscreen/PiP refused. **A video that can't be filtered plays unfiltered (owner's decision, 2026-11-08; the one exception to "fails closed" — images still stay hidden).** `Player.releaseVideo` marks the video `data-ifs-unfiltered` (the hide rule `video:not([data-ifs-unfiltered])` in `IFS.ELEMENT_CSS` and the `page-world.js` copy stops matching), hides the overlay, puts the page's own `playsinline`/PiP/AirPlay attributes back, and `page-world.js` lets that video use fullscreen/PiP. Two cases: (1) **frames unreadable** (cross-origin without CORS, or DRM — `checkCanvas` throws `SecurityError` from `toDataURL`): unfiltered, no more checks, until a new source (`emptied` / `src` change) removes the marker and starts again hidden + filtered. (2) **Checks failing** (server/engine down: `r.failed`, or a thrown timeout): after `FAIL_GRACE_MS` (2 s) of failures in a row **while the video plays** (a paused video stays hidden; one success resets the run) it is released, then probed every `PROBE_MS` (2 s); the first check that works calls `resumeFiltering` (marker off, presentation locked again, native fullscreen/PiP left, overlay drawn in the same task). A check that hangs (20 s timeout) keeps the video hidden until it times out. Disabling filtering removes the marker. Verified with a harness (same- vs cross-origin no-CORS video, mock server up/down/flaky/throwing, pause/play, src swaps, disable/enable, fullscreen/PiP gating); not yet tried in real Safari / on an iPhone. Measured ~6.8 fps for one video on the simulator (tiled 'fast'); two videos share the engine.
  - Filtered outputs are encoded with `canvas.toBlob` → `blob:` URL (`IFS.canvasToUrl`), not `toDataURL`: a synchronous JPEG encode plus 0.3–0.6 MB strings in inline styles stalled long pages.
  - Checks time out after 20 s (`withTimeout`) so a lost background reply can't leave a picture hidden forever; failures retry with back-off.
  - **Not covered:** canvas-drawn images (maps, editors), `<object>`/`<embed>` SVG documents' external images, external `<use>` sprites inside inline SVG (vector icons), closed *declarative* shadow roots, vector-only changes inside an approved inline SVG made by attribute animation (re-checked, not hidden), and any page the extension isn't running on — on iOS sites it isn't allowed on, and a page that loads while Safari is (re)starting the extension right after an install/update (measured: video visible ~0.4 s). `content: url()` introduced by a stylesheet that loads later can show until the next probe.
- **Base64 POST, not URL redirect** — Unlike MB Filter (which uses `declarativeNetRequest` redirects), this extension converts images to base64 via canvas and POSTs them. This is intentional: Safari's `declarativeNetRequest` support is limited, and using browser fetch avoids SSL certificate issues on the Python server. Where the pixels come from (server engine): (1) the page's own already-decoded `<img>` if readable (same-origin/CORS) — no second download; (2) a CORS copy; (3) if the site doesn't allow CORS, `background.js` `fetchAsJpegDataUrl` fetches it with host permissions (Safari's cache/cookies, decodes AVIF/HEIC) and encodes at the content script's `maxDim`; (4) only if that fails does the server download the URL. Server-engine encodes use at least 512px (`SERVER_MIN_ENCODE_DIM`) so tiling has pixels to work with.
- **Concurrent request limit** — `MAX_CONCURRENT = 10` in `content.js` limits in-flight requests; images beyond this limit are picked up on the next 250ms scan cycle.
- **Bundle ID** — `FelzyTech.Image-Filter-Service` used in native messaging and app launch coordination.
- **Background waits for stored config (`configReady`)** — Safari on iOS unloads the background page aggressively, and the message that wakes it is handled *before* `browser.storage` has been read. Every handler that depends on config (`filterImage`, `getConfig`, `updateConfig`, `checkServer`) awaits `configReady`; otherwise the first requests after each wake use the built-in default URL / ignore the disabled toggle. (Found by testing in the iOS Simulator: with a dead saved URL, images were still revealed via the default server.)
- **Failed images are retried by the content script** — `retryFailedImages` in `content.js` re-queues `failed` images every 5 s, doubling up to 60 s while they keep failing, and immediately when the server URL changes. The background's `serverOnline` push only works while its health polling is alive (macOS, local server), so a remote server (always the case on iPhone) relies on this. Images stay hidden throughout.
- **Health polling only for a local server** — the 5 s ping / 500 ms recovery polling exists to auto-start the server on this Mac, so it only runs when `serverUrl` is localhost (always the case on the Mac). Health checks use the configured URL's root, not a hard-coded `127.0.0.1:10000`.
